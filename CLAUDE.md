# CLAUDE.md

Hyperliquid developer tooling hub: read-only diagnostic tools (asset resolver, signing inspector, CoreWriter workbench, cross-layer trace, order composer/explainer, WebSocket workbench, RPC probe, multisig inspector) on one protocol core, plus the two sections that sign with a connected wallet: the multisig signer (`/multisig`: create a treasury from one's own account, change its signers, propose, sign, submit native multi-sig actions; with an optional Supabase relay for sign-in, shared treasuries, live proposals, nicknames and a "while you were away" notice; a signed-in treasury page shows the account live from Hyperliquid) and the original testnet faucet miner. See README.md for the user-facing overview, DECISIONS.md for why things are built this way, TESTING.md for what was verified.

## Commands

```bash
bun install
bun --bun run dev       # port 3000
bun --bun run build
bun --bun run check     # Biome lint + format
bun --bun run test      # vitest: core (packages/*) + app (src/**/*.test.ts) via vitest.config.ts
bun run db:start        # local relay (Supabase CLI + Docker); also db:stop, db:reset
bun run db:test         # pgTAP: supabase/tests/*.sql against the local database
bun run test:relay      # relay client against the local stack (src/**/*.itest.ts)
```

## Layout

- `packages/hl-core/` (`@hl-tools/core`, consumed as TS source): identifiers, `Decimal`, order-preserving JSON, MsgPack, signing, resolver, CoreWriter codec/precompiles, orders, trace, WS (`src/ws/`: channel specs and sessions for the workbench, plus `hub.ts`, the shared socket with liveness and reconnection, and `account.ts`, typed account rows and their merge), info and explorer adapters, RPC probe, multisig (`src/multisig/`: proposal document, digests, signatures, readiness, envelope, codec, diagnosis, `order.ts` for actions Hyperliquid takes only in order, and `transfer.ts` for account modes, where a send lands and the activation fee), versioned rules (`src/rules/`). No React. Tests in `test/`, fixtures in `fixtures/`, recorders/generators in `scripts/`.
- `src/routes/`: `index.tsx` (directory + paste box), `changes.tsx`, `tools/*.tsx`, `multisig/` (signer: `index` landing or inbox, `open`, `add`, `create`, `t.$network.$address`, `propose`, `proposal`; `route.tsx` mounts wallet, relay session and shell), `privacy.tsx` and `faucet-miner/`. The wallet providers are mounted only by those two layouts (`route.tsx`), each with its own wagmi config (`src/lib/wagmiConfig.ts` for the faucet miner, `src/lib/signerWagmiConfig.ts` for the signer); MSW mocks only by the faucet miner. `routeTree.gen.ts` is generated.
- `src/components/hub/`: shared design system (ToolPage, Panel, Callout, CodeBlock, HexView, DiffView, `Hint` for a "?" that explains a term…). `src/components/tools/<tool>/`: tool UIs.
- `src/lib/tools.ts`: tool registry (titles, samples, rule sets, primary sources). `src/store/networkStore.ts`: global network (persisted; use `useNetworkHydrated` before acting on it).
- Multisig signer: `src/components/multisig/` (screens and wallet hooks) over `src/components/multisig/model/` (pure and tested, no React: action builders, chain ids, nonce, transport, history, submit, stage, `send.ts` and `sendCheck.ts` for what a send costs and whether Hyperliquid would refuse it, `pageNetwork.ts` and `repropose.ts` for which network a form is for, `mode.ts` for the account mode in words and the balance figures, `signerSet.ts` for choosing signers and their three levels, `convert.ts` for the conversion an account signs itself, `create.ts` and `change.ts` for every sentence of the wizard and of Change signers, `lookups.ts` for the paced signer look-ups, `selfTreasury.ts` for the "treasury itself" tag and sentence; `model/relay/` is the relay's pure half: `wallets.ts` and `identity.ts` for the session slot per wallet and which one is in use, row parsers, assembling a proposal from rows, what to push, inbox groups, signer comparison, schedules, history sentences, nicknames, seen marks, the "while you were away" notice, copy; `model/chain/` is table columns and tying ledger rows to proposals; `model/live/` the per-account store; `model/help.ts` every hint text). `relay/` is the relay runtime (`client.ts`, `session.ts`, typed reads and writes in `api.ts`, the wallet's channel in `realtime.ts`, `RelayProvider`); `live/` is Hyperliquid's side (the socket hub per network, account, control, receiver, transaction look-up, self-treasury and signer-check hooks; it must never import the relay, a test guards this); screens live in `shell/` (frame, `DataTable`, `Help`), `inbox/`, `treasury/` (Overview, Pending, Signing log, On Hyperliquid), `away/`, `names/`, `add/`, `create/` (the wizard), `signers/` (what the wizard and Change signers share), `proposal/`, `propose/`. It reuses the inspector's review (`src/components/tools/multisig/{useJudgement,EnvelopeView}`); the inspector must never import from it, so the wallet stack stays out of read-only chunks. Shared helpers: `src/lib/idb.ts` (one IndexedDB, stores `wsSessions` and `proposals`), `src/lib/share.ts`, `src/lib/download.ts`. Test keys for app suites: `src/test/keys.ts`.
- `supabase/`: the optional relay. `migrations/` (hand-written SQL: tables with RLS, guards raising `relay.*`, the look-up worker and its queue, live pings, cron), `tests/` (pgTAP, shared helpers in `_helpers.inc`), `config.toml` (local stack). Stores: `src/store/{multisigPrefsStore,walletBusyStore,networkHintStore}.ts`.
- Faucet miner logic: `src/lib/hlActions.ts`, `src/hooks/useAutoChain.ts`, `src/components/{AutoMode,WalletTable}.tsx`.

## Conventions

Biome (tabs, double quotes). TS strict. Import alias `#/*` → `src/*`. Read-only everywhere except the faucet miner and the multisig signer. Signing UIs never hold or generate keys: the connected wallet signs. Never put pasted payloads in URLs; proposal documents travel in the URL fragment, a file or IndexedDB, never in a query string (`?digest=`, `?treasury=`, `?network=`, `?kind=`, `?supersedes=` are public identifiers). The signer's pages contact only Hyperliquid and, when someone signs in, the relay: `src/lib/signerWallets.ts` lists only wallets in the browser, so keep out RainbowKit's generic WalletConnect wallet (its modal reports the page URL to a third party), every entry with a WalletConnect QR fallback (MetaMask, Rainbow) and Coinbase's pop-up (a test builds the wagmi config and checks its connectors). No page loads a font, stylesheet or script from another host (`src/lib/thirdParty.test.ts`; the fonts are bundled). Every fetched result shows its network and observation time. A persisted store's "restored" flag goes through `usePersistHydrated` (`src/store/hydrated.ts`), never through the store's state at first render: a lazily loaded route can hydrate after the store was restored. Every browser bug in core logic becomes a fixture or test. When a protocol rule changes, bump its rule set's `version`/`verifiedAt` and changelog.

In the Multisig section: a page that signs takes its network from its link (`shell/usePageNetwork.ts` over `model/pageNetwork.ts`: the link wins on open, the header wins when moved, a link without one gets it written in), never from the header alone, every link to the propose form or the wizard passes `network`, the form is keyed by network, treasury, kind and the proposal it re-proposes, and a proposal is never copied to another network or treasury (`model/repropose.ts`). Messages use `<IssueList plain>` (no rule codes; the inspector keeps them) and `model/refusal.ts` for an answer the catalogue does not know. A stored proposal's unsigned fields (title, note) are never changed by a merge. Money is never polled (it arrives over the socket), and "none on record" is said only after a transaction was compared, never on a request that did not answer. What the screens say about the relay lives in `model/relay/copy.ts` and the help texts in `model/help.ts`; both are tested against a list of forbidden claims (private, encrypted, only you, free, no server), so add wording there, not inline. A nickname is "used only in this treasury" and is always shown with its address. Times are local in the section with UTC on hover; exports and the developer tools stay UTC. Hyperliquid takes an account's `usdSend`s only in increasing order of `time`, and a bridge withdrawal only after its latest send (`multisig/order.ts`, measured in `fixtures/multisig/nonce-order.json`): anything that lists or submits pending sends has to respect that, and a new send or withdrawal is numbered after every one on record (`orderFloor`). A submission Hyperliquid refused has used up the proposal's number (`numberSpent`): never offer to send the same proposal again. The two guided sends build `sendAsset` (`model/actions.ts`); `usdSend` and `spotSend` exist only as raw JSON and in older proposals. Which balance a send leaves, where it lands and what it costs depend on the treasury's account mode and on whether the receiver is new: the rules are the core's (`multisig/transfer.ts`, `rules/transfers.ts`, measured in `fixtures/multisig/send-modes.json` and `activation-fee.json`), the page's sentences are `model/send.ts`. A bridge withdrawal pays 1 USDC out of its amount and one of 1 USDC or less is refused (`withdrawalOutcome` in `multisig/transfer.ts`, `rules/transfers.ts`); its ledger row is tied to its proposal by `nonce`, with no look-up (`model/chain/match.ts`). The mode is read, never assumed (`useControl`; unread means warn, not guess), and a unified treasury has one balance (`balanceView` in `model/mode.ts`). Nothing is submitted before `checkBeforeSubmit` has asked Hyperliquid whether it would refuse; a read that fails stops nothing. Creating and changing a treasury use three levels and nothing else: blocked only where Hyperliquid itself would refuse (button off, reason beside it), a warning as one amber line with no click, plain facts otherwise; never a pop-up, an "I understand" checkbox or typed confirmation. The wizard converts the signed-in wallet's own account (in a build without a relay: the connected wallet) and never reasons from a second identity; a conversion's signature must recover to that account before it is sent, and a request that got no answer is settled by reading the signer list. A signer change is one `convertToMultiSigUser` carrying the whole new set, its form holds the action's own `signers` string, and what it does to waiting proposals is judged against the live signer list. A page follows one treasury at a time (`LiveAccounts` in `model/live/account.ts`) and subscribes to no more of it than the screen shows; a change there is checked against the frames the page really sends.

Relay: optional at build time (no `VITE_SUPABASE_*` means no sign-in and no supabase-js) and never trusted (the browser verifies every document and signature and judges readiness against the chain). Only `relay/client.ts` imports supabase-js, dynamically; `src/lib/boundaries.test.ts` enforces that and that nothing outside the Multisig section imports `relay/`. An account may ask for itself to be added once it is a multi-sig (`relay_self_register`); it still reads nothing of its treasury. Several wallets stay signed in in one browser, each in its own slot with its own client (`model/relay/wallets.ts`, `relay/client.ts`: one client per wallet, never a session swapped inside a client); the relay is in use as the connected wallet only, after `whoami()` confirmed its stored session, and which wallet that is comes from one pure rule (`model/relay/identity.ts`: answers carry the count they were asked under and late ones are dropped). A parked wallet makes no request and renews nothing. Signing out empties the slot first, then ends the session on the relay (`endSession`); never rely on the relay answering to clear the browser. Clients insert rows and call no RPC other than `whoami()`; every change to a policy, grant, trigger or guard needs a pgTAP case, and `supabase db advisors --local` stays clean. Sentences about what is stored live in `model/relay/copy.ts` and never say private, encrypted, only you, free or no server. Local stack only: no hosted Supabase project is touched from here. Relay sign-in needs the app opened as `http://localhost:3000`, not `127.0.0.1`. New migrations: `supabase migration new <name> < /dev/null`.
