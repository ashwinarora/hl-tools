# CLAUDE.md

Hyperliquid developer tooling hub: read-only diagnostic tools (asset resolver, signing inspector, CoreWriter workbench, cross-layer trace, order composer/explainer, WebSocket workbench, RPC probe, multisig inspector) on one protocol core, plus the two sections that sign with a connected wallet: the multisig signer (`/multisig`: create a treasury from one's own account, change its signers, propose, sign, submit native multi-sig actions, vault deposits and withdrawals among them; with an optional Supabase relay for sign-in, shared treasuries, live proposals, nicknames and a "while you were away" notice; a signed-in treasury page shows the account live from Hyperliquid) and the original testnet faucet miner. See README.md for the user-facing overview, DECISIONS.md for why things are built this way, TESTING.md for what was verified.

## Commands

```bash
bun install
bun --bun run dev       # port 3000
bun --bun run build
bun --bun run check     # Biome lint + format
bun --bun run test      # vitest: core (packages/*) + app (src/**/*.test.ts) via vitest.config.ts
bun run db:start        # local relay (Supabase CLI + Docker); also db:stop, db:reset
bun run db:test         # pgTAP: supabase/tests/*.sql against the local database
bun run test:relay      # relay client against the local stack (src/**/*.itest.ts)
bun run rpc:1337        # the signing network's stand-in on its own, localhost:3337 (the app serves it at /rpc/1337; vault forms need VITE_CHAIN_1337_RPC_URL)
```

## Layout

- `packages/hl-core/` (`@hl-tools/core`, consumed as TS source): identifiers, `Decimal`, order-preserving JSON, MsgPack, signing, resolver (`resolver/outcomes.ts`: an outcome share's name from Hyperliquid's lists), CoreWriter codec/precompiles, orders, trace, WS (`src/ws/`: channel specs and sessions for the workbench, plus `hub.ts`, the shared socket with liveness and reconnection, and `account.ts`, typed account rows and their merge), info and explorer adapters, RPC probe, multisig (`src/multisig/`: proposal document, digests, signatures, readiness, envelope, codec, diagnosis, `order.ts` for actions Hyperliquid takes only in order, `transfer.ts` for account modes, where a send lands and the activation fee, `staking.ts` for what Hyperliquid reports about staking, the steps a staking form needs and what Hyperliquid would answer to them, `vault.ts` for vault amounts, reads, the one-or-two-step planner and what Hyperliquid would answer, `move.ts` for two proposals that are one move, `receipt.ts` for whose word a receipt is, `shown.ts` for text somebody else wrote and `when.ts` for dates that never throw), versioned rules (`src/rules/`). No React. Tests in `test/`, fixtures in `fixtures/`, recorders/generators in `scripts/`.
- `src/routes/`: `index.tsx` (directory + paste box), `changes.tsx`, `tools/*.tsx`, `multisig/` (signer: `index` landing or inbox, `open`, `add`, `create`, `t.$network.$address`, `propose`, `proposal`, `glossary`; `route.tsx` mounts wallet, relay session and shell), `privacy.tsx`, `faucet-miner/` and `rpc/1337.ts` (the signing network's link, a server route). `src/start.ts` is the request middleware: every response's security headers (`src/lib/securityHeaders.ts`) and the nonce the router writes on its scripts (`ssr.nonce` in `src/router.tsx`). The wallet providers are mounted only by those two layouts (`route.tsx`), each with its own wagmi config (`src/lib/wagmiConfig.ts` for the faucet miner, `src/lib/signerWagmiConfig.ts` for the signer); MSW mocks only by the faucet miner. `routeTree.gen.ts` is generated.
- `src/components/hub/`: shared design system (ToolPage, Panel, Callout, CodeBlock, HexView, DiffView, `Hint` for a "?" that explains a term…). `src/components/tools/<tool>/`: tool UIs.
- `src/lib/tools.ts`: tool registry (titles, samples, rule sets, primary sources). `src/store/networkStore.ts`: global network (persisted; use `useNetworkHydrated` before acting on it).
- Multisig signer: `src/components/multisig/` (screens and wallet hooks) over `src/components/multisig/model/` (pure and tested, no React: action builders, chain ids, nonce, transport, history, submit, stage, `send.ts` and `sendCheck.ts` for what a send costs and whether Hyperliquid would refuse it, `pageNetwork.ts` and `repropose.ts` for which network a form is for, `mode.ts` for the account mode in words and the balance figures, `signerSet.ts` for choosing signers and their three levels, `convert.ts` for the conversion an account signs itself, `create.ts` and `change.ts` for every sentence of the wizard and of Change signers, `lookups.ts` for the paced signer look-ups, `selfTreasury.ts` for the "treasury itself" tag and sentence, `staking.ts` for the three staking forms and the Staking tab's rows, `vault.ts` for the two vault forms and the Vaults tab's rows, `signingNetwork.ts` for the chain an action is signed under, the code a wallet shows and the switch-or-add sequence, `modeSwitch.ts` for the account-mode form, `drafts.ts` for what a half-filled form keeps, `move.ts` for a move's state and for one row per move, `notices.ts` for which notices of a proposal page stay open and which fold, `guide.ts` for the first-run card, the start page's ways in and the glossary, `outcomes.ts` for the outcome shares among a treasury's balances, `proposalTimeline.ts` for a proposal's timeline, `toasts.ts` for what a toast says; `model/relay/` is the relay's pure half: `wallets.ts` and `identity.ts` for the session slot per wallet and which one is in use, `positions.ts` for a signer's no and what it does to a proposal, row parsers, assembling a proposal from rows, what to push, `serial.ts` for one push at a time, inbox groups, signer comparison, schedules, history sentences, nicknames, seen marks, the "while you were away" notice, copy; `model/chain/` is table columns, tying ledger rows to proposals and, in `stakingRecord.ts` and `vaultRecord.ts`, reading from the staking history or the ledger whether a step was carried out, `record.ts` and `recordCopy.ts` for an accepted proposal against Hyperliquid's record, `csv.ts` for the "On Hyperliquid" tables as CSV; `model/live/` the per-account store; `model/help.ts` every hint text). `relay/` is the relay runtime (`client.ts`, `session.ts`, typed reads and writes in `api.ts`, the wallet's channel in `realtime.ts`, `RelayProvider`); `live/` is Hyperliquid's side (the socket hub per network, account, control, receiver, transaction look-up, self-treasury and signer-check hooks; it must never import the relay, a test guards this); screens live in `shell/` (frame, `DataTable`, `Help`, `Slow` for a wait that runs long, `Heard` for a result announced and scrolled into view, `Split` and `useStickyTop` for a side column that stays in view, `Headline` and `Facts` for a proposal's confirmation block, `MultisigMark`), `inbox/`, `treasury/` (Overview, Pending, Staking, Vaults, Signing log, On Hyperliquid), `away/`, `names/`, `add/`, `create/` (the wizard), `signers/` (what the wizard and Change signers share), `proposal/`, `propose/`. It reuses the inspector's review (`src/components/tools/multisig/{useJudgement,EnvelopeView}`); the inspector must never import from it, so the wallet stack stays out of read-only chunks. Shared helpers: `src/lib/idb.ts` (one IndexedDB, stores `wsSessions` and `proposals`), `src/lib/share.ts`, `src/lib/download.ts` (also `toCsv`), `src/lib/tabs.ts` (the keys of a row of tabs), `src/lib/signingRpc.ts` (the answers of the signing network's stand-in and their HTTP exchange, `signingRpcResponse`; served at `/rpc/1337` and by `scripts/signing-network-rpc.ts`). Test keys for app suites: `src/test/keys.ts`.
- `supabase/`: the optional relay. `migrations/` (hand-written SQL: tables with RLS, guards raising `relay.*`, the look-up worker and its queue, live pings, cron), `tests/` (pgTAP, shared helpers in `_helpers.inc`), `config.toml` (local stack). Stores: `src/store/{multisigPrefsStore,multisigDraftsStore,walletBusyStore,networkHintStore}.ts`.
- Faucet miner logic: `src/lib/hlActions.ts`, `src/hooks/useAutoChain.ts`, `src/components/{AutoMode,WalletTable}.tsx`. Its mock's service worker is `dev/mockServiceWorker.js`, served by the dev server only (`devMockWorker` in `vite.config.ts`), never put in `public/`.

## Conventions

Biome (tabs, double quotes). TS strict. Import alias `#/*` → `src/*`. Read-only everywhere except the faucet miner and the multisig signer. Signing UIs never hold or generate keys: the connected wallet signs. Never put pasted payloads in URLs; proposal documents travel in the URL fragment, a file or IndexedDB, never in a query string (`?digest=`, `?treasury=`, `?network=`, `?kind=`, `?supersedes=`, `?agent=` (an API wallet's name) and `?vault=` are public identifiers). The signer's pages contact only Hyperliquid and, when someone signs in, the relay: `src/lib/signerWallets.ts` lists only wallets in the browser, so keep out RainbowKit's generic WalletConnect wallet (its modal reports the page URL to a third party), every entry with a WalletConnect QR fallback (MetaMask, Rainbow) and Coinbase's pop-up (a test builds the wagmi config and checks its connectors). No page loads a font, stylesheet or script from another host (`src/lib/thirdParty.test.ts`; the fonts are bundled). Every response carries `securityHeaders` (`src/start.ts`); in production its Content-Security-Policy lets scripts run only from the site and inline only with that response's nonce, so an inline script of our own takes `useRouter().options.ssr?.nonce` (as the two in `__root.tsx` do) and nothing runs from an event-handler attribute or another host. `connect-src` stays open to any https and wss host on purpose (the RPC probe and the WebSocket workbench reach whatever endpoint they are given, and one page's policy holds for the whole visit); a local build also names the configured relay and 1337 origins (`configuredOrigins`). The development server sends no policy, so a change that touches scripts, frames, fonts or new hosts is checked on a production build (`bun run build`, `bun run start`) with the console's policy violations. The signing network's link is `/rpc/1337` on the site and never changes: a wallet keeps the link it added. The app is AGPL-3.0-only (`LICENSE`), `packages/hl-core` MIT (its own `LICENSE`). Every fetched result shows its network and observation time. A persisted store's "restored" flag goes through `usePersistHydrated` (`src/store/hydrated.ts`), never through the store's state at first render: a lazily loaded route can hydrate after the store was restored. Every browser bug in core logic becomes a fixture or test. When a protocol rule changes, bump its rule set's `version`/`verifiedAt` and changelog.

In the Multisig section: a page that signs takes its network from its link (`shell/usePageNetwork.ts` over `model/pageNetwork.ts`: the link wins on open, the header wins when moved, a link without one gets it written in), never from the header alone, every link to the propose form or the wizard passes `network`, the form is keyed by network, treasury, kind and the proposal it re-proposes, and a proposal is never copied to another network or treasury (`model/repropose.ts`). Messages use `<IssueList plain>` (no rule codes; the inspector keeps them) and `model/refusal.ts` for an answer the catalogue does not know. A sign-in that did not finish is one toast (`model/relay/signInNotice.ts`): a short line, the exact reason folded under "Details", never written next to the button. Every result of a wallet or sharing-service action is also said in a toast (`model/toasts.ts`, `shell/notify.ts`), whatever the page shows: a success closes after four seconds, a failure after eight with its first reason, both by themselves; the page keeps its own line, and a push the page makes in the background raises none (the relay buttons answer with their own issue). A stored proposal's unsigned fields (title, note) are never changed by a merge. Money is never polled (it arrives over the socket), with two stated exceptions: staking figures and vault deposits are on none of the channels the page listens to, so they are read over HTTP once a minute while shown, like the signers (`live/useStaking.ts`, `live/useVaults.ts`, "Updated … ago" with its own help text), and again when spot HYPE changes or a step was just accepted. The "while you were away" notice is the third: for each treasury of the wallet it reads the transfers since the signer's mark over HTTP (`away/useAway.ts`), at most once in five minutes, because no socket follows a treasury that is not on screen. "None on record" is said only after a transaction was compared, never on a request that did not answer. A receipt in a copy opened from a link or a file counts only when `checkReceipt` (core `multisig/receipt.ts`) finds its signature to be the finaliser's; `saveProposal` leaves any other out. A receipt read from the relay is taken as filed (the relay holds only the signatures their signers put there, so the check cannot be made from its rows). The check says who sent a proposal, never what Hyperliquid answered (the answer is outside the signature): a reported refusal does not offer "propose it again" where the account's ledger holds the action or one like it (`ledgerEvidence` in `model/chain/match.ts`; `carriedOut.seenBy: "ledger"` and `likeOnRecord` in `model/stage.ts`), and a proposal page follows the ledger for a proposal the relay does not hold as well. A text somebody else wrote (a validator's or a vault's name, a title, a note) is read through `shownLine`/`shownNote` in the core; a text that is signed or that names something exactly (an API wallet's name, a field of an action) is shown through `visibleText`, never trimmed of anything. A request body pasted into the inspector is judged over Hyperliquid's own writing of its inner action, as a document is (`requestAsJudged` in `multisig/envelope.ts`; measured in `fixtures/multisig/inner-form.json`): never judge a signature over an action as pasted. A value from a pasted document may be a bigint (an integer too large for a number): write one out with `written` and compare with `deepEqual`, never with `JSON.stringify`. A name put into a sentence goes through `isolated` (inline in a screen: `<bdi>`), and is cut with `cutTo`, never with `slice`. A vault other than HLP shows its name as a quotation; HLP is told by its address. Live figures that are not live show `LiveAccount.asOf`. What the screens say about the relay lives in `model/relay/copy.ts` and the help texts in `model/help.ts`; both are tested against a list of forbidden claims (private, encrypted, only you, free, no server), so add wording there, not inline. The screens use the section's own words: "Send to Hyperliquid" (never "submit"), "Cancel for everyone", "sharing service" (never "relay"), "Hyperliquid's record" (never "ledger" or "the chain"), "proposal number" and "what everyone signs" (nonce, digest, envelope and EIP-712 only under "For experts"); `jargon.test.ts` fails on anything else in a sentence on screen, and a line that must use such a word says why in a `jargon:` comment. A title in the section is the brand's teal (`BRAND_TEXT`): `Card`, and `Panel` taken from `shell/kit` (never the hub's directly), so the diagnostic tools keep theirs. The glossary and the first-run card are `model/guide.ts`; the card folds to its title (it never disappears) and its steps also head the glossary. Hiding a treasury is a choice in the "⋯" menu beside its name (`treasury/TreasuryMenu.tsx`), with Undo, never a button among sentences. A proposal page carries its timeline (`model/proposalTimeline.ts`, `proposal/TimelineCard.tsx`): the sharing service's history of the proposal (already read with it), or a copy's own dates, never naming a copy's proposer; one wallet's entries within ten seconds are one step; Hyperliquid's record joins only where the page reads it already, after the send it records. Once nothing can be signed or sent (`FINISHED` in `model/stage.ts`, a move's `settled`) the share panel is one "Download a copy". A proposal page shows what must not be missed in full and folds the rest into "N notes" (`model/notices.ts`: never fold a stop notice); its bottom bar on a phone only brings "Your part" into view. A sign or send result goes through `Heard`. Layout: the section and the site's header and footer share one 1,440 px container (`MULTISIG_WRAP` in `src/components/Header.tsx`); a column that stays in view clears the sticky site header and sticks only while it fits (`useStickyTop`); the Preview of what will be signed and the buttons that act on it are never inside a box with its own scrollbar or under a pinned element (the exact action, folded for experts, may scroll inside its code block); a proposal page opens with its status, then the confirmation block with the amount as the largest figure and addresses whole. A wait on the relay ends after 10 seconds, and a long one shows `Slow` with a way out. Pushes to the relay go through the queue of `model/relay/serial.ts`, one per wallet and proposal, marked pending before the copy is saved; a write re-reads only that proposal and the open list. Wherever a proposal reads as accepted (its page, the Signing log, "While you were away") the browser checks it against Hyperliquid's record, the explorer's list of the account's newest 300 transactions (`model/chain/record.ts`); the relay never asks Hyperliquid, and "no transaction" is said only when the list reaches back past the send. CSV exports (`toCsv`) are in UTC, every figure to its last decimal, with the formula guard; a vault row is "likely" there too. A nickname is "used only in this treasury" and is always shown with its address. Times are local in the section with UTC on hover; exports and the developer tools stay UTC. Hyperliquid takes an account's `usdSend`s only in increasing order of `time`, and a bridge withdrawal only after its latest send (`multisig/order.ts`, measured in `fixtures/multisig/nonce-order.json`): anything that lists or submits pending sends has to respect that, and a new send or withdrawal is numbered after every one on record (`orderFloor`). A submission Hyperliquid refused has used up the proposal's number (`numberSpent`): never offer to send the same proposal again. The two guided sends build `sendAsset` (`model/actions.ts`); `usdSend` and `spotSend` exist only as raw JSON and in older proposals. Which balance a send leaves, where it lands and what it costs depend on the treasury's account mode and on whether the receiver is new: the rules are the core's (`multisig/transfer.ts`, `rules/transfers.ts`, measured in `fixtures/multisig/send-modes.json` and `activation-fee.json`), the page's sentences are `model/send.ts`. A bridge withdrawal pays 1 USDC out of its amount and one of 1 USDC or less is refused (`withdrawalOutcome` in `multisig/transfer.ts`, `rules/transfers.ts`); its ledger row is tied to its proposal by `nonce`, with no look-up (`model/chain/match.ts`). The mode is read, never assumed (`useControl`; unread means warn, not guess), and a unified treasury has one balance (`balanceView` in `model/mode.ts`). Nothing is submitted before `checkBeforeSubmit` has asked Hyperliquid whether it would refuse; a read that fails stops nothing. Creating and changing a treasury use three levels and nothing else: blocked only where Hyperliquid itself would refuse (button off, reason beside it), a warning as one amber line with no click, plain facts otherwise; never a pop-up, an "I understand" checkbox or typed confirmation. The wizard converts the signed-in wallet's own account (in a build without a relay: the connected wallet) and never reasons from a second identity; a conversion's signature must recover to that account before it is sent, and a request that got no answer is settled by reading the signer list. A signer change is one `convertToMultiSigUser` carrying the whole new set, its form holds the action's own `signers` string, and what it does to waiting proposals is judged against the live signer list. Staking: the three forms ask for the end result and work out one proposal or two (`model/staking.ts` over the core's `multisig/staking.ts`; waits and limits in `rules/staking.ts`, each marked measured or from the docs; the lab record `fixtures/multisig/staking.json` is replayed). Two proposals are a move: tied by the unsigned `meta.steps` and believed only through `judgeMove` (same network, treasury, finaliser and proposer, numbered in order, and exactly one of the three staking shapes or a move to perps followed by a vault deposit, the one move whose second step is signed as a code), so never show, count or submit two proposals as one on `meta.steps` alone. A move is one row and one page; its relay writes go through the pair functions of `relay/api.ts` (both rows in one statement, both or neither); the finaliser gives every signature before anything is posted and step 2 is posted only after Hyperliquid accepted step 1 (`finaliseMove`). An unstake inside the lockup can be signed but not submitted (`heldUntil` in `model/stage.ts`). A move leaves the page whole: the share with co-signers (`shareMove`), a link and a file always carry both steps. Proposed again from its second step a move is that step alone (`formFromProposal`), never the whole move. A stake and an unstake leave no ledger row, so whether a step was carried out is read from the staking history (`model/chain/stakingRecord.ts`); a return that lands is Hyperliquid's own step. A step is never said to be "not carried out" when Hyperliquid answered "duplicate nonce" or the staking history holds a step like it that the explorer did not confirm (`unsure` in `model/move.ts`). A lockup is judged by Hyperliquid's own clock before an unstake is sent (`clock` in `SendReads`). A list tags a lone step only through `loneStep`, and names a staking action through `actionLine` (the validator's own name with its short address). Validators are shown as Hyperliquid reports them, never ranked or recommended; one that pays nothing gets one amber line; a total stake is cut to whole HYPE and the expected rate is the 7-day one, as on Hyperliquid's page. A step in the staking history from before a proposal was made is never taken for that proposal's (`madeAt` in `stakingCandidates`). The explorer is asked through `live/explorerList.ts` and nothing else: the account's newest transactions in one `userDetails` request (the latest 300, no paging), shared by `useTxLookups` (the transaction behind a row) and `useRecords` (an accepted proposal against Hyperliquid's record), and `txDetails` for a single transaction only where `model/chain/accountTxs.ts` says the list cannot have it; callers pass the account with each hash. `txDetails` has a daily allowance per network address: its refusal is `ExplorerAllowanceError`, never "not found", and nothing is then asked singly for ten minutes and nothing retried. Vaults: a `vaultTransfer` is the one action of the code family (Hyperliquid's L1 actions) this section signs; every other one stays "inspect only" and Raw JSON refuses them all. It is signed as `Agent {source, connectionId}` under chain 1337, which a wallet has to hold as a network: `model/signingNetwork.ts` decides the chain an action is signed under (`signingChainOf`) apart from the envelope's (`envelopeChainOf`, always an ordinary chain, so a finaliser who adds no signature never needs 1337), goes to the wallet directly for the switch and the add (wagmi refuses a chain outside its config) and puts the wallet back afterwards (`chainAfterSigning`). The page shows the code the wallet will show (`proposal/CodePanel.tsx`) wherever a vault step is signed. A build without `VITE_CHAIN_1337_RPC_URL` offers no vault form anywhere (`kindOffered`) and says a vault proposal can be read, not signed. A vault action carries no number of its own: never tie a ledger row to a vault proposal as more than "likely" (`model/chain/match.ts`), never say a vault step was not carried out when the ledger holds one like it (`model/chain/vaultRecord.ts`), and the relay refuses a "carried out" report for one (`relay.report_unnumbered`); only the finaliser's own result or the proposer's withdrawal closes it. The forms ask for the end result and work out one proposal or two (`model/vault.ts` over the core's `multisig/vault.ts`; minimum, HLP's address and lockups in `rules/vaults.ts`, each marked measured or from the docs; the lab record `fixtures/multisig/vaults.json` is replayed). A withdrawal inside the lockup can be signed and not submitted; one whose lockup ends after the proposal would close is refused in the form and said in amber on its page (`closesFirst` in `model/stage.ts`). HLP by name, any vault by address, shown as Hyperliquid reports it, never ranked or recommended. What a withdrawal can take is `maxWithdrawable` (`vaultDetails` with the depositor's address: the precise value cut down to 6 decimals), never `userVaultEquities.equity`, which can be above it (measured on mainnet 2026-10-19); the form's list says "releases …" from it. Money is never rounded: an amount signed is exactly what was typed or what Max filled; a figure shown is cut toward zero (`usdcShown`, `amountText`), and one the cut would turn to nothing is shown whole; a JSON number from Hyperliquid is read as `String(v)` and then cut, never through `toFixed`; comparisons and conversions are `Decimal`, never floats. An outcome share ("+<encoding>" among the spot balances, `outcomeShare`) is shown under the Overview's Outcomes tab, named by the core's `outcomeName` from `outcomeMeta` and `outcomeTemplates` (read only while the treasury holds one, kept ten minutes: metadata, not money), and never under Balances, counted as a token or offered to send. Every amount field has a "Max" (`model/max.ts`, tested against the core's fee rules; `propose/MaxButton.tsx`): the most Hyperliquid would take now from its own figures, cut down to the action's decimals, a fee off only where the same balance pays it, nothing filled while what it depends on is unread (the destination of a send, the account mode), and the check before sending compares again. API wallets are read with `InfoClient.apiWallets` (the named ones from `extraAgents`, the one without a name from `webData3`), never from `extraAgents` alone; removing one is `approveAgent` with the zero address and its name (`isAgentRemoval`). A mode switch is `userSetAbstraction` both ways, and its envelope is hashed over a one-letter code (`hashedEnvelopeAction` in `multisig/digest.ts`, letters in `rules/multisig.ts`, measured in `fixtures/multisig/mode-switch.json`): add a letter only when it was measured. A send to a HyperEVM system address is refused from a multi-sig (`multiSigEvmRefusal`, `isSystemAddress` in `rules/hyperevm.ts`). A half-filled form is kept in localStorage for a week (`store/multisigDraftsStore.ts`, rules in `model/drafts.ts`): written from the form's setters, never from an effect on its state, a link that asks for something else wins, and its one sentence does not say more than "This browser keeps it for a week." A sentence about an action may hold a colon: a page shows a line as a field and its value only through `labelledLine` (`model/parts.ts`). A moment shown in the reader's time is rendered only once the page runs in the browser (the server has another clock and locale). A page follows one treasury at a time (`LiveAccounts` in `model/live/account.ts`) and subscribes to no more of it than the screen shows (`tabWants` in `model/tabs.ts` says what each section of a treasury page follows, and whether its ledger rows are looked up on the explorer); a change there is checked against the frames the page really sends. The Vaults tab's history is the ledger's vault rows (`vaultHistory`), whoever made them, with the "Proposal" cell "On Hyperliquid" has (`treasury/ledgerCells.tsx`); it asks Hyperliquid for nothing new. "While you were away" is about what the signers decided and who can act for the treasury: it announces an API wallet's approval and removal, never what an API wallet did (a vault deposit made by one is a row "none on record" in that history).

Relay: optional at build time (no `VITE_SUPABASE_*` means no sign-in and no supabase-js) and never trusted (the browser verifies every document and signature and judges readiness against the chain). Only `relay/client.ts` imports supabase-js, dynamically; `src/lib/boundaries.test.ts` enforces that and that nothing outside the Multisig section imports `relay/`. An account may ask for itself to be added once it is a multi-sig (`relay_self_register`); once added, it reads what its signers read (`relay_treasury_reads_itself`: `private.my_treasuries()` includes the wallet's own treasury, and its pings reach it) and writes nothing (every write stays on `private.is_signer()`); the app never asks it to sign (`inboxGroup`), keeps no read marks for it and shows it no "While you were away" (both are a signer's). Several wallets stay signed in in one browser, each in its own slot with its own client (`model/relay/wallets.ts`, `relay/client.ts`: one client per wallet, never a session swapped inside a client); the relay is in use as the connected wallet only, after `whoami()` confirmed its stored session, and which wallet that is comes from one pure rule (`model/relay/identity.ts`: answers carry the count they were asked under and late ones are dropped). A parked wallet makes no request and renews nothing. Signing out empties the slot first, then ends the session on the relay (`endSession`); never rely on the relay answering to clear the browser. The relay answers only for a session that still exists (`relay_live_sessions`): `private.current_wallet()` requires the token's `session_id` in `auth.sessions`, and PostgREST's pre-request `gate.live_session()` refuses an ended session with HTTP 401 `relay.session_ended`, which each wallet's client listens for (`watchFetch`, `onSessionEnded`). Never read the user from the token in a policy or a function of your own (`auth.uid()`, `auth.jwt()`): go through `private.current_wallet()`; pgTAP `150_live_sessions.sql` fails otherwise. pgTAP wallets get a session from `tests.make_wallet`. A signer's no (`public.objections`, `model/relay/positions.ts` for the rule and every sentence) is an objection, never an ending: nothing but its proposer's withdrawal closes a proposal (the relay refuses a decline), a proposal held up by a no stays open, and no text is ever stored with a no. One position per signer per proposal (nothing, a signature, or a no), kept by the relay's triggers. A wallet's read markers are written one statement at a time (`relay_read_mark_turn`: a statement trigger takes the wallet's lock before any row has its id, because the newest id is the marker); a lock taken in a row trigger comes too late to order ids. The relay stores one action of the code family, a `vaultTransfer` in its exact shape and filed as kind "l1" (`relay_vault_proposals`, mirrored by `model/relay/push.ts`). A result the relay refuses because it already holds the proposal as accepted is done, not a problem (`settledAlready`). Clients insert rows and call no RPC other than `whoami()`; every change to a policy, grant, trigger or guard needs a pgTAP case, and `supabase db advisors --local` stays clean. Sentences about what is stored live in `model/relay/copy.ts` and never say private, encrypted, only you, free or no server. The hosted project (Free plan, no session limit: a known gap, Pro's own setting when that changes) is set up by its owner by hand; from here it is only read, and only when asked. Its Auth settings live in the dashboard, not in `config.toml` (which is the local stack's and says localhost): site URL, Ethereum sign-in, the allowed sign-in addresses, the custom access token hook `private.on_token_issued` and the web3 sign-in rate limit. An address other than the site URL's host signs in only when the allowed list holds it twice, without and with a trailing slash: Supabase checks the message's URI as written and its domain rebuilt as `https://<domain>/` (skipped for `localhost`, which is why the local stack never shows it). Relay sign-in needs the app opened as `http://localhost:3000`, not `127.0.0.1`. New migrations: `supabase migration new <name> < /dev/null`.
