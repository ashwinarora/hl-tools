# Decisions

Non-obvious choices made while turning hl-tools into a developer tooling hub, and why. Newest decisions are appended at the end of each section.

## Architecture

**`@hl-tools/core` is a Bun workspace package consumed as TypeScript source.** `packages/hl-core/package.json` exports `./src/index.ts` directly; Vite and Vitest compile it, so there is no separate build step or `dist/` to go stale. It has its own `tsconfig` (with `noUncheckedIndexedAccess`, stricter than the app) and its own Vitest config.

**Branded identifiers carry the network in the type.** `ActionAssetId<"mainnet">` is not assignable to `ActionAssetId<"testnet">`. Brands are erased at runtime, so every record also keeps a `network` field and `assertNetwork()` re-checks at boundaries. Resolved results are stamped with the network they came from; the UI drops a selection when the global network changes instead of re-interpreting it.

**Exact decimals are a small in-house `Decimal` (bigint mantissa + scale), not a library.** The protocol needs parse, add/sub/mul, divide-with-explicit-rounding, significant-figure and decimal-place rounding, and exact scaling to/from integers (CoreWriter 1e8, USD 1e6). A ~400-line class with exhaustive tests is easier to audit than a general-purpose library, and it refuses floats entirely (`Decimal.fromInteger(0.1)` throws).

**An order- and lexeme-preserving JSON parser sits in front of signing.** `JSON.parse` reorders integer-like keys, turns `1.0` into `1` and truncates integers above 2^53. All three change the MsgPack bytes and therefore the hash, so the Signing Inspector parses pasted payloads with `parseJson`, which keeps key order, raw number lexemes and source offsets (for error positions).

**MsgPack is implemented in core with byte spans.** The SDK's encoder is correct but opaque. hl-core's encoder matches Python `msgpack.packb` (smallest int formats, float64 for non-integers) and records which bytes belong to which field, which the inspector uses for highlighting and for reporting the first divergent field in compare mode. A decoder is included for round-trip tests and for pasting raw bytes.

**Canonical L1 action shapes come from the Python SDK, not from the TS SDK's valibot schemas.** The server re-serialises the action it parsed, so key order, trailing zeros and address case must match what it produces. The TS SDK's schemas silently "fix" inputs and don't model priority grouping (`{"p": n}`), so hl-core keeps its own shape table (`canonical.ts`) that *reports* each difference and can produce the canonical form.

**Signing vectors are generated from the official Python SDK.** `packages/hl-core/scripts/gen_signing_vectors.py` re-derives the SDK's published test vectors (so every field is present, not just r/s/v) and adds vectors for cancel, cancelByCloid, bracket orders with builder + expiresAfter, spot orders, modify, vault orders, usdSend, approveAgent (named/unnamed), approveBuilderFee, usdClassTransfer, sendAsset, spotSend and tokenDelegate, on both networks. The key is the SDK's own public test key; it only exists in that script. All 49 vectors pass byte-for-byte.

**Metadata is normalised by explicit IDs.** Spot pairs and tokens are keyed by their `index` field — on both networks the array position differs from `index` (verified 2026-09-28), so positional lookup silently returns the wrong asset. Perps have no identifier other than their position in a dex's `universe` (the protocol defines the asset ID that way), so the position is read exactly once during normalisation and stored as `perpIndex`. HIP-3 dex indexes come from `perpDexs` and are cross-checked against the `dex:` prefix of the coins in `allPerpMetas`; a dex whose metadata doesn't line up is dropped with a warning rather than guessed.

**The resolver never auto-selects.** Any query with more than one match is flagged ambiguous and the detail panel stays empty until the user picks. "BTC" is ambiguous on mainnet because several HIP-3 dexes list a `BTC` market; "HYPE" matches a perp, five spot pairs, the token and a HIP-3 market. A single match is shown directly.

**Outcome size decimals are shown as "unknown".** `outcomeMeta` does not publish `szDecimals` for outcome tokens. Rather than infer them from the book, the resolver renders a first-class "unknown" value and the example order uses a whole-number size with an explicit warning.

**CoreWriter units were confirmed against live transactions.** A mainnet usdClassTransfer with `ntl = 10000000` produced a ledger `accountClassTransfer` of `"10.0"` USDC (so `ntl` is 1e6-scaled), and a mainnet limit order with `limitPx = 266710000000`, `sz = 500000` and a cloid matched an order at `2667.1` / `0.005` in `historicalOrders` with the same cloid (1e8 scaling; cloid is the link between layers).

## App shell

**Wallet stack only on `/faucet-miner`.** Initially wagmi + RainbowKit + WalletConnect were mounted at the root, so every read-only tool page called web3modal, WalletConnect's `pulse` telemetry endpoint and an Ethereum RPC. That contradicts "nothing leaves the browser / excluded from analytics", so the providers moved into a `/faucet-miner` layout route. Tool pages now contact only the Hyperliquid APIs, the HyperEVM RPCs the user chooses, and Google Fonts. This also fixed a hydration mismatch (RainbowKit's theme `<style>` differed between server and client).

**MSW mock mode is scoped to the faucet miner and stopped on leave.** It used to start from the root when `localStorage.mock === "1"`, which would have silently fed mocked data to every diagnostic tool.

**Network choice is persisted in localStorage and painted before hydration.** An inline script copies the stored network onto `<html data-network>`; the switch's active segment is styled from that attribute, so the correct segment renders on first paint without a hydration mismatch. The Zustand store uses `skipHydration` and rehydrates after mount.

**Pasted input moves between pages through an in-memory store, never the URL.** The homepage "paste anything" box detects the input type locally and hands it to the target tool via a non-persisted Zustand store. Only non-sensitive inputs (asset queries) are mirrored into the URL (`?q=`). Sample buttons use `?sample=<id>`, which references a built-in sample rather than carrying content.

**No analytics.** The app ships no analytics. Inputs that can hold payloads carry `data-private` so any future analytics integration has an explicit exclusion hook.

**TanStack devtools are opt-in in development** (`?devtools=1` or `localStorage.devtools = "1"`) so the floating launcher doesn't cover tool UI in screenshots.

**Typefaces: Geist + Geist Mono**, bundled with the site (`@fontsource-variable`), with system fallbacks. Geist's tabular figures and Geist Mono's clear `0/O` and `1/l` matter for hex and IDs. They came from Google Fonts at first, which gave Google every visitor's address and the page's origin on each load (found by the audit of 2026-10-12); `src/lib/thirdParty.test.ts` now keeps other hosts out of the document head and the stylesheet.

**Design tokens.** A cool neutral ramp, one brand accent (mint), and five semantic roles. "Unknown / unsupported" is violet with a dashed border so it can never be mistaken for an error (red) or a warning (amber). Mainnet and testnet have their own colours (green / amber dot) used by every network badge.

**Sharing uses the URL fragment, behind an explicit confirmation.** The Signing Inspector and the failure explainer can share their input, but only after the user ticks "this content is public". The state goes into `#share=<base64url>`, which browsers never send to the server or in `Referer`, and it is stripped from the address bar as soon as the receiving page has read it. Samples use `?sample=<id>` instead, which names a built-in sample and carries no content.

**"Try with a sample" always shows a result.** A sample that only prefilled inputs made two tools look empty on arrival, so the RPC probe runs its sample comparison and the WebSocket Workbench connects on arrival. Both are bounded, read-only and public. Samples that carry a network (the testnet `usdSend` vector, testnet trace hashes) switch the global network *after* the stored preference has been restored, so the preference cannot override them a moment later.

**`useNetworkHydrated` rehydrates its own store.** Sample logic waits for the persisted network. Relying only on the root layout's `rehydrate()` call proved fragile: during server rendering zustand attaches no `persist` API at all (localStorage is unavailable), which crashed SSR, and in development Vite can load a second copy of the store module after a hot update, so the listener never fired. The hook now tolerates a missing API and calls `rehydrate()` itself; it's an idempotent localStorage read.

**Radio groups follow the WAI-ARIA pattern.** The network switch and every segmented control are button-based radio groups (to keep the segmented styling); arrow keys, Home and End move the selection and only the checked option is a tab stop. Shared in `src/lib/radioGroup.ts`.

**The faucet miner keeps its behaviour and adopts the shell.** Its logic is unchanged. Only presentation moved: hub `ToolPage` header with the same verified-date/source block, a warning callout stating it is the one tool that signs, theme tokens instead of hard-coded amber/red text, and RainbowKit's button only once a wallet is connected (the landing hero already offers Connect Wallet). The old `/how-to-use` URL 301-redirects to `/faucet-miner/how-to-use`.

**Template leftovers removed.** The initial TanStack Start template shipped a public `POST /mcp` route with an `addTodo` demo that wrote `mcp-todos.json` to disk. It had nothing to do with the product and was a writable endpoint on a public site, so it was deleted with its dependencies (`@modelcontextprotocol/sdk`, `zod`).

**The wallet stack is mounted by two layouts, each with its own configuration.** The Multisig Signer is the second section that connects a wallet, so `/multisig` has its own layout route that mounts `WalletProviders` as `/faucet-miner` does; the read-only tools still never load wagmi, RainbowKit or WalletConnect (checked in the production build: the wallet code sits in its own chunk that neither the entry nor the inspector references). The first version shared the faucet miner's wagmi config. That was wrong for a signing page, for the reason in the next entry, so the signer now has `src/lib/signerWagmiConfig.ts`: the chains a proposal can name as its signing chain (HyperEVM 999 / 998, Arbitrum One / Sepolia; a wallet can only be asked to switch to a chain the config knows) plus Ethereum, so that connecting does not move a wallet that is on Ethereum. It keeps its connection state under its own storage key. The faucet miner's config is unchanged from before the signer existed.

**The signer's pages contact Hyperliquid and nothing else.** Measured in the browser: with the shared config, every signer page load sent a request to `pulse.walletconnect.org` whose body contained `window.location.href`, and after connecting, an ENS lookup for the signer's address went to a public Ethereum RPC. The first comes from RainbowKit's generic "WalletConnect" wallet: it is the one entry that makes `@walletconnect/ethereum-provider` create a Reown AppKit modal as soon as the config exists, AppKit reports an `INITIALIZE` analytics event with the page URL, and nothing in the options that reach it turns analytics off. On the signer that URL names the treasury (`?treasury=`) or the proposal (`?digest=`), and a proposal link holds the whole document in its fragment until the page strips it; in the measured run the fragment was already gone when the event fired, but only by timing. The second comes from RainbowKit's account modal, which resolves a name on chain 1 whenever chain 1 is configured. So the signer's wallet list dropped the WalletConnect entry (`src/lib/signerWallets.ts`, guarded by a test), and its Ethereum transport answers locally instead of calling out. The faucet miner keeps the generic entry and therefore its beacon; its URLs carry nothing.

**The signer's wallet picker offers the wallets in this browser, and nothing that reaches a third party.** The first list kept RainbowKit's MetaMask, Rainbow and Base Account entries. The audit of 2026-10-12 measured what they do for a visitor without the extension: MetaMask and Rainbow fall back to a WalletConnect QR code, which opens a socket to `relay.walletconnect.org` on that click and, because the choice is remembered, on every later page load; Base Account opens a pop-up at `keys.coinbase.com`. All three are gone. What is left: the wallets that announce themselves (EIP-6963, detected by RainbowKit), a wallet that only injects ("Browser Wallet", offered only when nothing announced itself, since next to an announced wallet it is a second door to the same one), and Safe inside a Safe app's frame. The test builds a real wagmi configuration and checks that its connectors are exactly `injected` and `safe`. The price: a desktop browser with no wallet extension cannot connect a phone wallet by QR code here. Such a visitor is told "No wallet was found in this browser…" under the buttons, which then no longer open an empty picker.

**The signer has its own wallet button.** RainbowKit's stock `ConnectButton` resolves an ENS name, avatar and balance over an Ethereum RPC on every render. Nothing in the signer needs them. `WalletBar` uses RainbowKit only for the wallet picker and shows the lowercase short address, the chain the wallet is on and a disconnect button.

**The header links every section that signs, from the registry.** The faucet link was hard-coded; the header now renders one link per tool with `writes: true`, and the home pill reads "read-only unless a card says Signs & sends" so the promise stays true with two such cards.

**One IndexedDB database, one helper, two stores.** `src/lib/idb.ts` used to open `hl-tools` v1 with a single `wsSessions` store. The signer's proposal history needed a second store, and two modules opening the same database at different versions would block each other, so the helper owns the schema: version 2, an idempotent upgrade that creates whichever store is missing (a v1 database keeps its sessions; tested), a clear message when another tab blocks the upgrade, and a generic `idbRequest` both features use.

## Tools

**Signing Inspector samples are generated from the Python SDK vectors.** `scripts/gen_signing_samples.py` turns vectors into full request bodies (`src/samples/signing.ts`), so every sample's signature really recovers to the SDK's public test address and a sample can never drift from what the tests check. The inspector has no private-key field; it only hashes and recovers.

**Compare mode reports the first divergent byte, not just a text diff.** Two payloads that look identical as JSON can hash differently (`"100"` vs `"100.0"`, key order). The compare view encodes both with byte spans and names the field containing the first differing byte, then shows the JSON diff for context.

**The Signing Inspector hands multisig envelopes to the multisig module.** Detected `multiSig` payloads get an explicit diagnostic pointing at `envelopeDigest` / `classifySignatures` (and, from Phase 1, the Multisig Inspector) instead of a wrong hash. The inspector itself still hashes single-signer actions only.

**CoreWriter decoding never guesses.** An unknown version byte, an undefined action id and malformed ABI data each produce their own explicit result (`unknown-version`, `unknown-action`, `malformed`). The body of an unknown version is not decoded. The builder refuses human inputs that are not exactly representable at the action's scale (e.g. `limitPx` with more than 8 decimals) rather than truncating.

**Trace conclusions carry evidence labels.** Each link is `observed` (read from the chain or info API), `inferred` (derived by a stated rule, e.g. matching an order without cloid by coin/side/price/size/time) or `unknown`. A cloid makes a limit order observable via `orderStatus`; without one the match is inferred and labelled so. Limit orders, `usdClassTransfer` and `sendAsset`/`spotSend` are traced; other decoded actions say "trace not supported for this action yet". A hash that isn't on the selected network is looked up on the other network and reported, but the tool never switches networks on its own.

**Trace timing is reported with its resolution.** HyperEVM block timestamps are whole seconds, so "+0.437 s after the block" carries a "(block time has 1 s resolution)" caveat.

**The composer never rounds user input.** An invalid price or size blocks the payload and offers the nearest valid values in each direction with the delta; the user picks one. A positive size that rounds to zero lots is a prominent blocking error. Values the composer derives itself (market price = mid ± slippage) are rounded in the conservative direction (buys down, sells up) and the rounding is shown. Sizes and prices are `Decimal` end to end; prefills from live mids never pass through floats.

**The failure explainer treats `"status":"ok"` as the start, not the answer.** A batch response is explained per status entry, a single error for a multi-order request is flagged as a whole-batch pre-validation rejection, and a truncated response is reported as malformed JSON rather than matched against the error catalogue.

**WebSocket reconnect analysis is honest about what the protocol allows.** No Hyperliquid channel has sequence numbers or a resume cursor (stated per channel in the ordering table). After a simulated disconnect the workbench diffs state before and after; for `trades` it compares the re-subscribe replay with REST `recentTrades` to count what was missed. That `trades` replays recent trades on subscribe without an `isSnapshot` flag was found while testing and encoded in websocket rules 1.1.0.

**Recorded sessions are bounded and sanitised.** Recording stops at 5,000 messages, 8 MB or 30 minutes; IndexedDB keeps the 20 newest sessions. Exports replace every address with a stable pseudonym (`0x000…0001`, …) and imports are strictly validated (format, version, monotonic timestamps) with a specific reason on rejection.

**The RPC probe decides "historical" with exact controls.** Comparing a historical answer with the latest one only shows they differ. The probe uses a nonce oracle instead: a transaction from X with nonce n in block B proves X's nonce at B−1 was exactly n. It also checks that a well-known contract (USDC) has no code at block 1000. Public HyperEVM RPCs failed both on 2026-09-28 (they answer historical queries with latest state) and are flagged. dRPC passed.

**The probe is bounded, paced and runs `eth_getLogs` last.** Around 25 requests, 250 ms apart, for the public endpoint's 100 requests/minute limit. Large log ranges exhausted the public testnet limit for the checks after them, so the range probe now runs last. A rate-limited check is reported as "inconclusive · rate limited", never as unsupported. Endpoint URLs are shown redacted (`?apikey=•••`) and are never persisted or put in the page URL; a CORS-blocked endpoint aborts with an explanation.

**The resolver surfaces wrapped assets by substring, below exact matches.** Spot BTC on Hyperliquid is the token `UBTC`, so an exact-name resolver showed no spot market for "BTC". Queries of three or more alphanumerics now also match perps, spot bases and tokens whose name *contains* the query, labelled "name contains the query" and ranked below every exact match. Pair queries (`UBTC/USDC`) and dex-prefixed queries never use it. Delisted markets always sort after live ones regardless of score.

**Composer intents are listed simplest first and IOC is the default.** The TP/SL brackets were first because they are the richest demo, but a first-time user meets the most complex payload first. Order is now IOC → post-only → market → reduce-only close → long TP/SL → short TP/SL.

**The limit price shows its relation to the live mid.** Whether an IOC fills or a post-only is rejected depends on where the price sits against the mid, so the price field's hint states the mid, the percentage distance and "would take" / "would rest" (amber when it would take), with a Use-mid shortcut. The mid is informational; the composer still never changes a typed price.

**Format/Minify in the Signing Inspector go through the order-preserving parser.** `JSON.parse` + `JSON.stringify` would reorder integer-like keys and rewrite `1.0` as `1`, changing the bytes hashed. `parseJson` → `stringifyJson` keeps key order and number lexemes, so reformatting is guaranteed not to change the digest (verified: digest identical before and after).

**Precompile index parameters can be filled by name.** Nobody knows HYPE is token 150 or perp 159. Each perp/spot/token/asset parameter has a name search backed by the resolver, filtered to the identities that parameter accepts, showing the index each option maps to. The numeric field stays editable and the "resolves to" line confirms the mapping.

**Decoded precompile output is the headline; the raw JSON-RPC is collapsed.** A user read the hex `result` in the raw block and concluded the output wasn't human-readable, even though the decoded table sat above it. The table now has a title and field/raw/human headers, and the raw exchange is behind a disclosure.

**The faucet miner is a regular directory card plus a header link.** It was in a separate "Also in the hub" section to mark it as the one tool that signs; the owner found that read as second-class. It now sits in the main grid with its "Signs & sends" badge and has a direct header link.

**Similar names are suggestions, not candidates: they never make a query ambiguous.** After substring matching was added, "HYPE" reported 16 ambiguous identities, 9 of which were KHYPE, STHYPE and friends; the count alarmed more than it informed. The resolver now exposes `isSimilarMatch` and computes `ambiguous` over direct matches only. The UI lists direct matches first, then a "Similar names" section, and the market picker does the same; "BTC" is still ambiguous (the perp plus HIP-3 BTC markets), "ETH" plus its six look-alikes is not. A query with no direct match says so instead of pretending the look-alikes are matches.

**"Use mid" writes a valid price, rounded towards the resting side.** Mids carry more significant figures than an order may (84654.5 on BTC), so inserting the mid verbatim produced an immediately blocked payload. The shortcut rounds to the market's tick, down for buys and up for sells, so the inserted price never crosses the mid just by rounding. This is the one place the composer rounds, and it is a button the user presses, not a typed value.

**The signing verdict never promises a digest that doesn't exist.** A bare action without a nonce showed "the digest below is what a wallet would sign" above an empty pipeline. The verdict now says what is missing, and the nonce field offers "Use now" (the current millisecond timestamp, as a client would send) so a pasted action can be walked through without inventing a number.

**Modes and public identifiers live in the URL; payloads never do.** CoreWriter and Orders keep their tab in `?tab=`, and a trace keeps its transaction hash in `?tx=`, so a reload or a shared link lands on the same view. Pasted bytes, responses and signatures still travel only through the in-memory handoff or an explicit Share link.

**Index fields in the CoreWriter builder are searchable by name**, with the same resolver-backed search the precompile panel uses; it moved to `components/hub/IndexSearch` so both share one implementation.

**Unknown paths get a real page.** TanStack's default not-found component rendered a bare "Not Found" inside the shell; the hub now renders its own page listing every tool.

**The resolver teaches the vocabulary, not just the answer.** Hyperliquid has five identifier families that overlap in one text box (coin string, action asset ID, display symbol, token, outcome encoding), and the page used to show the result without naming any of them. `classifyQuery` in the core names the shape of what was typed from its syntax alone, before any network call, so `@107`, `#83061`, `100083061` and a bare `150` each get a one-line explanation and the spellings that follow from the input itself. The identity card is a "spelling · value · used in" table from `identitySpellings`, with the API word first (`exchange a`, `spotSend / sendAsset`) and plain words on hover. A "Same asset elsewhere" row from `relatedIdentities` lets the user hop perp → spot → token in place, and the legend at the bottom of the page holds the whole model with live examples. A separate glossary page was rejected: the confusion happens while resolving, so the explanation has to sit next to the result.

**Settled outcomes are looked up, not reported as missing.** `outcomeMeta` lists only live outcomes; a 60-second BTC binary that settled is gone from it, and so are its book, mids and candles. The API keeps the spec and result behind `settledOutcome`, so an outcome-shaped query (`#…`, `+…`, `100000000 + …`) that has no live match falls back to it and shows both sides with their payout per share, stamped with network and observation time and a "settled" badge. A live or unknown outcome returns null from that endpoint, and the page says "neither live nor settled" rather than "nothing found". Verified against mainnet outcome 8306 (recorded as a fixture).

**Search params are kept as the strings they were typed.** TanStack Router's default codec JSON-parses each value, so `?q=100083061` reached the route as a number, failed its string check and was dropped; once accepted it was re-serialised as `?q=%22100083061%22`. The router now parses values as-is and never quotes strings. Every search param in the app is a string, and the faucet miner reads its `?mock=1` through `URLSearchParams` directly, so it is unaffected.

**EVM → Core token transfers are verified, not just counted.** A contract that pays out through Circle's `CoreDepositWallet.depositFor` never touches CoreWriter: the only EVM evidence is a `Transfer(from, to = system address, value)` log from the token's linked contract, and HyperCore credits the `from` address, which is neither the transaction sender nor the calling contract. On testnet such transfers can be dropped with no error on either side, and the page used to show the same output for a credited and a dropped one. The trace now resolves the token from `spotMeta` by the emitting contract (decimals = `weiDecimals + evmExtraWeiDecimals`, system address = `0x20…<index>`), then makes one `userNonFundingLedgerUpdates` query per credited account and matches a `spotTransfer` from the system address with the same token, amount and destination at or after the block. A match is `observed` with the ledger time; no match is `inferred` as "No HyperCore credit observed", downgraded to "Not credited yet" when the block is under a minute old; an unlinked emitter or a failed query is `unknown` with the reason. The page reports whether a credit was observed and never asserts a cause: the protocol does not state one. Native HYPE sent to `0x2222…2222` emits no log and is not detected, which the rule set says. Rule set `evm-core-transfers@1.0.0` carries the sources.

**Reference material is not a finding.** "Why CoreWriter actions fail silently" sat under the verdict of a transaction with no CoreWriter action, and the owner of the game contract read it as a diagnosis of a payout that had in fact succeeded. On such transactions it is now a collapsed reference block that says so in its title, the CoreWriter gas note is only shown when a CoreWriter action exists, and the transfer line in the receipt reads "8 USDC → HyperCore spot of 0x7b67…496e" instead of raw units and the system address.

**Bare addresses route to the Multisig Inspector.** The paste box used to send a 40-hex address to the asset resolver, where it matched nothing. An address is an account, and the inspector answers for every account: a multi-sig gets its signers, a normal user, agent, vault or sub-account gets its role explained. 32-hex token IDs still go to the resolver.

**The Multisig Inspector stores nothing.** Every number is fetched from Hyperliquid when the user looks and stamped with its network and observation time; the only cache is TanStack Query's 10 s. There is no table to drift from the chain, and later phases add storage only for what the chain cannot answer (proposals and signatures that have not been submitted yet).

**One account lookup costs 64 of the 1200 weight per minute; the rest is conditional or on demand.** `userToMultiSigSigners` 20, `extraAgents` 20, `clearinghouseState` 2, `spotClearinghouseState` 2, `openOrders` 20, in one `Promise.allSettled` so a failed section never blanks the others. `userRole` (60) runs only when the address is not a multi-sig, because then the role is the explanation. Per-signer nesting checks (20 each, at most 10), the HyperEVM balance and explorer history (40) are buttons, and the raw-requests panel lists every call with its weight. There is no auto-refresh.

**Explorer history is capped and attributed with a caveat.** `userDetails` on `rpc.hyperliquid(-testnet).xyz/explorer` is CORS-open and returns the newest ~101 entries with no paging, so the panel says "showing the most recent N". The explorer records envelope actions against the multi-sig user without the leader or the signatures, so history can show *what* the account did but never *who* signed; the panel says that too.

**The envelope view takes the network from the payload when the payload carries one.** User-signed inner actions name it in `hyperliquidChain`, so the view pins that network, warns when the header disagrees and fetches the signer set there. L1 payloads carry no network: the header decides, the page says so, and when the multi-sig user does not exist there the view probes the other network and offers a one-click switch instead of reporting "unknown".

**A raw envelope has no claimed signers, so recovery decides.** Proposal documents name each signer; exchange request bodies carry only `{r, s, v}`. The core treats a zero-address claim as "unclaimed": the signature is attributed to whoever it recovers to, and the diagnosis accepts a variant when it recovers to any current authorized user. Found in the browser (every signature of a pasted envelope showed as invalid) and fixed in core with tests, per the hub rule.

**Signatures render as stacked rows, not a table.** Index, recovered address, status and the reason do not fit four columns in a half-width workspace: the address either wrapped one hex pair per line or pushed the reason behind a horizontal scroll. One row per signature with the reason underneath reads at every width.

**The Multisig Signer is a section, not a tool tab.** Diagnosing a multi-sig (`/tools/multisig`) is read-only and needs no wallet; proposing, signing and submitting need one and move funds. Keeping them apart keeps the wallet stack out of the read-only pages and makes the "Signs & sends" boundary a URL boundary (`/multisig`). The review a signer sees is the inspector's own: `useJudgement` and `ProposalResult` were lifted out of the envelope view so both pages recover, attribute and count signatures with the same code against the same live signer set. The inspector never imports from the signer.

**The signer proposes user-signed actions and, of the actions signed as a code, the vault deposit and withdrawal alone.** A treasury exists to govern funds: sends, perps ↔ spot transfers, withdrawals, staking, the decision to delegate trading to an agent key, and (Phase 6, part 3) putting USDC into a vault and taking it out. For a user-signed action the wallet shows the destination, amount, multi-sig user and leader as typed fields, which is the signer's independent check of what the page claims. A vault action is of the other family, the one Hyperliquid's docs call L1 actions: it is signed as a hash under chain 1337, so the wallet shows a code and nothing else. It was left out for that reason and is in now, because a treasury that cannot reach HLP is missing an ordinary treasury action; what the page does about the lost check is under "A vault action is signed as a code" below. Orders, cancels, leverage and every other action of that family stay out: a multi-sig that trades does it through an approved agent anyway. Raw JSON is accepted for the other user-signed types the core canonicalises. It refuses an action of the code family (`raw.l1_out_of_scope`), and it refuses the three actions that have a guarded form of their own and points to that form: a vault action (`raw.vault_out_of_scope`), a change of signers (`raw.convert_out_of_scope`) and a mode switch (`raw.mode_switch_out_of_scope`). The proposal page states "An L1 action: inspect only" for a pasted document of that family that is not a plain vault action, instead of offering to sign it.

**The leader is the finaliser, chosen per proposal, with no default.** The chain fixes the leader inside every inner signature, and the leader need not have proposed. Choosing the signer who will *complete* the threshold means that person signs the inner payload, signs the envelope and submits in one sitting, and nobody makes a return trip. The form asks "Who finalises this?", lists the current signer set and starts empty, so "the proposer leads" never becomes the silent norm. When the finaliser's signature is the one that completes the threshold, the page offers a single "Sign and submit". If the finaliser disappears, the proposal is re-proposed (`meta.supersedes`) with another one. Rejected: issuing the same action under several leaders so whoever is free can finish, because leaders have separate nonce sets and a send could execute twice.

**Humans only in the signer set: no executor account, no auto-submit.** A service-held key could submit the moment the threshold is met, but the leader must be an authorized user or a funded agent of one. Either a signer hands a server a key that also trades their personal account, or a dedicated executor joins the signer set and whoever holds its key has a vote. A multi-sig cannot rest on a promise not to use a key, so the finaliser's own wallet always signs the envelope.

**The EIP-712 chain id is fixed when the proposal is created, and the envelope reuses it.** The inner `signatureChainId` is part of the action every signer signs; the chain never compares it with the network but a signature made under another id fails as "Invalid multi-sig inner signer" (testnet, lab script 18: 998, 999, 1 and 42161 all accepted when consistent). So the proposer picks it once: HyperEVM by default (999 / 998, where a Hyperliquid user's wallet usually already is), Arbitrum as the option. Signers are asked to switch only if their wallet is elsewhere. The envelope's own chain id is a free leader-time choice, so the finaliser signs it under the same chain and never switches twice; it is recorded in the receipt.

**Two signing windows: now, or dated 23 hours ahead.** The chain accepts a nonce from two days in the past to one day in the future. A nonce of "now" gives signers two days. A nonce 23 hours ahead is already submittable and stays so for almost three days, which the form offers as "give signers 3 days"; the missing hour is the margin against clock skew at the upper bound. The window is shown wherever the proposal is, with the time left.

**`vaultAddress` and `expiresAfter` are always null for user-signed proposals, and a document that sets them is refused.** Neither field is in the digest signers sign for a user-signed action, so two documents can share a digest and differ in them. The builder forces both to null, the proposal page refuses to sign or submit a document that sets either ("This document sets a vault address or an expiry"), and the history refuses to merge a copy with the same digest and a different payload (`history.payload_conflict`) instead of treating it as the same proposal.

**The proposal document is the only state a signer needs, and transport is an interface.** Without the relay (see "The relay" below) there is no backend: a proposal travels as a link (`#share=` fragment on `/multisig/proposal`, the hub's existing share scheme, never sent to a server and stripped as soon as it is read) or as a file, behind `ProposalTransport { publish, decode }`. The relay is a third way to carry the same document, and link/file stay as the path that works with nothing but a wallet. Getting a link still requires ticking an acknowledgement: signatures are not secrets, but the link reveals the intent to whoever holds it. Documents above 16 KiB get a "use the file" warning rather than a link that chat apps and browsers may cut. No QR code: a signed document is too dense for one.

**Per-browser history is keyed by digest and merged, never appended.** Opening a link, uploading a file or merging a returned copy all go through `saveProposal`, which loads the stored document with the same digest and runs the core's `mergeProposals` (union by recovered signer, unverifiable signatures dropped). A signer who opens yesterday's link again loses nothing, and a forged or tampered signature never reaches storage. A receipt is replaced only by a better one (accepted beats rejected, then the later attempt). The list says it is browser storage, not chain data. If IndexedDB is unavailable the page keeps the document in memory and says it is not saved.

**Readiness is judged again immediately before the envelope is signed.** The signer set is fetched fresh when the finaliser presses the button, signatures are re-classified against it, and only those that count go into the envelope. A rotation between review and submit therefore produces "not ready" in the page, not a chain rejection. A snapshot of the signer set taken at creation travels (unsigned) in the document only to say "the signer set changed since this was proposed".

**A rejected submission keeps its receipt, and ends the proposal.** The exchange answer is stored on the document with the envelope chain id and explained through the error catalogue (cause and fix), and the failed step is marked. Until Phase 4 the button stayed enabled, on the reasoning that the signatures remain valid until the window closes. The order lab showed that reasoning to be wrong: an envelope Hyperliquid took and refused has used up its number for that finaliser, whatever the reason (threshold not met, a stranger's signature, an action that failed for balance, a number outside the window), and sending it again is answered "Invalid nonce: duplicate nonce", three minutes later as well as at once, and also after what was wrong has been put right. So the page now says "Refused by Hyperliquid · cannot be sent again" with "Re-propose", offers no button that can only fail, and the inbox lists the proposal under "Cannot be finished" for everyone. Two answers leave the proposal as it was, because they never reached the finaliser's account: a transport failure (anything but HTTP 200) and an envelope signature that recovered to another address. The rule is the core's `numberSpent` (errors 1.4.0). "Insufficient balance for withdrawal." was not in the catalogue when the first real rejection came back; it was added to the core with a test (errors 1.2.0).

**A treasury's money arrives over one WebSocket; nothing about money is polled.** (Phase 4; until then the strip was polled every 30 seconds.) The core has a small socket hub, `ws/hub.ts`: one connection per network, subscriptions counted so two screens share one, its own liveness (ten quiet seconds bring a ping, ten more without an answer mean the socket is dead), reconnection on a slowing, jittered schedule from 1 to 30 seconds, resubscription with the first message treated as a fresh snapshot, and a server refusal turned into a state the page can show ("Live updates unavailable"). It is written in the core rather than wrapped around the SDK's transport, which reconnects underneath and hides both acknowledgements and liveness. On top of it the section keeps one store per account with three groups, each held only by a screen that shows it: `holdings` (balances, positions, open orders) while a treasury is on screen, `ledger` (deposits, withdrawals, transfers) while "On Hyperliquid" is open or a proposal is pending, and `trades` (fills, order history, funding) only while "On Hyperliquid" is open. A proposal page therefore holds four subscriptions, not seven. A tab hidden for a minute lets go of the socket and takes it back when looked at. The account comes from the URL, never from a row of the relay, so the money stays live when the relay is down.

**A page follows one treasury at a time.** Hyperliquid documents a cap of ten accounts per network address, which testnet and mainnet did not enforce when measured, and which the page treats as something that may be enforced any day. A group nobody wants is kept for three seconds, so that moving between two pages of the same treasury does not unsubscribe and subscribe again. That grace must not span two treasuries: the stores live in one registry (`LiveAccounts`), and the moment a screen starts following an account, everything still kept for any other account is let go at once, on the same socket and after the new subscriptions were asked for, so the socket is neither shared by two treasuries nor closed and reopened. The HTTP side follows the same rule by construction: the two control reads (signers, API wallets) and the transaction look-ups belong to the mounted screen, are cancelled when it unmounts, and a look-up still waiting for its turn is dropped. The one deliberate exception is the home screen's "While you were away", which reads two things for each of the wallet's first ten treasuries, once in five minutes (below).

**Who controls a treasury is asked for once a minute, over plain HTTP.** Signers and API wallets cost the same on either route and change rarely, so they are two requests a minute (weight 40 of 1200) while a treasury page is open, paused in a background tab and repeated at once when the tab is looked at. The boxes say "Checked … ago" and have a refresh button. The queries are the inspector's own (`policyQuery.ts`), so both share an answer, and the read immediately before an envelope is signed bypasses every cache.

**Live rows are merged, never replaced.** Hyperliquid re-sends the state channels every five seconds and sends history as a snapshot followed by a stream. `ws/account.ts` parses each channel into typed rows and `mergeRows` adds them to a table kept newest first: order-independent, idempotent (both are property-tested), capped at 500 rows, and returning the previous object when nothing changed so a table does not re-render every five seconds. After a reconnect the first snapshot is merged like any other message, and a table whose snapshot does not reach back to its older rows says that rows from the gap may be missing.

**Balance checks warn and never block.** An amount above the observed balance is a warning on the form: the balance is an observation that can be stale by the time the finaliser submits, and funding the treasury after proposing is legitimate. The chain is the authority and its rejection is explained.

**Wallet outcomes are inline; toasts only show progress.** A declined popup, an unsupported chain switch or a signature from the wrong account each render as a callout next to the button that caused it, with the document unchanged. The toast only says a wallet prompt is open. One busy flag guards every wallet action, so three quick clicks open one popup.

**The paste box sends proposal documents and signer links to the signer; envelopes and addresses stay with the inspector.** A document is something to act on, a request body is something to diagnose. Each page offers the other as a button ("Inspect", "Open in Multisig Signer"), handing the text over in memory, so neither is a dead end.

**Panels follow the stage.** `deriveStage` turns the document, the live judgement, the connected wallet and the clock into one phase with the reasons each button is or is not available. "Your signature" and "Finalise" render only in phases where they can act; an expired, submitted or unsupported proposal shows the stage callout with the next step (re-propose, check the ledger) instead of two disabled panels repeating it. A spot-token select of 1,668 entries lists the tokens the treasury holds first.

**The relay stores and gates; every browser verifies.** Phase 3 adds an optional backend (Supabase: Postgres, Auth, Realtime, Cron, in `supabase/`) so co-signers see each other's proposals and signatures without passing files around. It is not trusted with anything that matters: a browser decodes every document, recomputes its digest, recovers every signature and judges readiness against the live chain exactly as it does for a link or a file. A relay that lies can hide or delay; it cannot forge a signature, change what is signed or move funds. Rows that do not verify are ignored and the page says so (a signature filed under another signer's name, a document that no longer matches its digest, a column that disagrees with the document).

**The relay is optional twice: at build time and while running.** With `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` unset there is no sign-in anywhere and the section is the link-and-file signer of Phase 2. With them set, signing in is still a choice, and supabase-js is fetched only when someone signs in or has a stored session: `relay/client.ts` is the single runtime import, as a dynamic import, and `src/lib/boundaries.test.ts` fails the build if another file imports it, if anything outside the Multisig section reaches into `relay/`, or if the pure model imports the runtime. When the relay does not answer, the rail says so, links and files keep working, a cached proposal still opens and can be signed, and the page reconnects by itself (5 s, doubling to once a minute, and at once when the browser is back online or the tab is looked at). Found in the browser: the first version waited for a click on "Try again".

**Identity comes from `auth.identities`, never from the token.** Sign-in is Supabase's "Sign in with Ethereum": one message signed by the wallet. The address also lands in the user's metadata, which a user can edit, so no policy reads the JWT. `private.current_wallet()` looks the caller up in `auth.identities` and answers only when the user has exactly one identity and it is an Ethereum one; every policy compares against it, so a missing wallet fails closed. Supabase checks the message's domain and URI but keeps no nonce store and does not enforce the stated expiry: a signed message is accepted for ten minutes from its "Issued At". The message therefore says in words that it approves nothing and moves nothing, and the window is recorded in a test rather than assumed away.

**A session belongs to one wallet, and only the connected wallet's session is ever in use.** Every write function checks the session's wallet against the wallet the page thinks it is acting for before sending anything, and signing out is local to the browser. At first the browser kept one session: connecting another wallet suspended it (no relay request, no token renewal, no channel) and offered "Sign in as 0x…", which replaced it. Since 2026-10-12 each wallet keeps its own; see "Several wallets stay signed in" further down.

**Membership is a copy of the chain's signer list, refreshed by a worker inside Postgres.** A wallet sees a treasury when it is in the relay's stored copy of that treasury's signers. Nobody is invited and nothing is configured: add the address once and every co-signer who signs in sees it. The copy is kept current by one function run by `pg_cron` every two seconds that makes at most one `userToMultiSigSigners` call per run through the `http` extension (so at most 30 a minute, half of what Hyperliquid allows an IP), with timeouts, a back-off on errors, a 60 s pause on a 429, and two lanes so a burst of new treasuries cannot starve re-checks. What asks for a re-check, in priority order: an accepted `convertToMultiSigUser` recorded on the relay, a signer's browser that sees the live list differ from the copy, a sign-in or token renewal (a database hook leaves a mark; copies older than ten minutes are looked at again), and a daily sweep. A removed signer therefore loses access at the next look-up, with or without a visitor.

**A treasury that stops being a multi-sig is frozen, not deleted.** One `null` from Hyperliquid can be a glitch, so the copy is frozen only after two well-formed `null` answers at least 30 seconds apart, and anything malformed is a retry. A frozen treasury keeps its last known signers, who can still read its history; new proposals and signatures are refused, its open proposals stop appearing under "Needs you", and the page says "no longer a multi-sig" wherever it used to state the signer set. If the account becomes a multi-sig again the next look-up unfreezes it. Found in the browser: the page read "no signer set" as "not known yet" and never asked for the look-up; `livePolicy` now tells the two apart.

**Clients insert rows; they do not update, and the only function they call is `whoami()`.** Proposals, signatures, endings (withdrawn, declined) and receipts are insert-only, with column-level grants so identity columns cannot even be named and triggers that stamp them from `current_wallet()`. Taking a signature back was the one delete when this was written; a signer taking back a no is the second (see the entry on a signer's no). Asking for a look-up is a row in `treasury_requests` that the worker answers, not an RPC, so every entry point is a table with a policy and the security review is a list of tables. Proposal-side tables share the key `(network, treasury, digest)`: one access rule everywhere, and a signer of one treasury cannot occupy a digest that belongs to another. Guards raise stable `relay.*` messages that the client turns into sentences, and hourly caps (5 adds, 30 re-checks, 30 proposals per wallet; 50 open proposals per treasury) bound what a signer's key can write.

**Live updates are pings without content, one private channel per wallet.** When anything a wallet may see changes, a trigger broadcasts an empty "changed" to `wallet:<address>`; the browser answers by re-reading through the access rules. Nothing confidential travels on the socket, a newly added treasury notifies without a rejoin, a removed signer gets one last ping and then nothing, and joining another wallet's channel is refused. A ping is only a hint: joining counts as one, and the lists also refresh once a minute.

**Opening a link or a file sends nothing; sharing is a button.** A signed-in signer who opens a document somebody sent them has not asked for it to be stored anywhere, so the page says "This proposal is only in this browser" and offers to share it. Two things do go by themselves, both agreed in advance: a proposal created on the propose screen while signed in (that is what the screen is for), and Hyperliquid's answer after the finaliser submits (co-signers need to know it went through).

**The browser's history is still what the page renders; the relay's copy is written through it.** `useProposalDoc` merges the relay's verified copy into IndexedDB under a per-digest lock and renders from there, so link, file and relay signatures meet in one document and a proposal opened once keeps working offline. A signature made while the relay was unreachable is pushed when it returns. The one subtlety is taking a signature back: a copy of it may linger in some browser, so a signer whose latest relay event is "signature removed" is dropped from every local copy until they sign again.

**Take back, withdraw and decline are facts about the relay, not about the chain.** A signature already given stays valid on Hyperliquid until the signing window closes, and only the finaliser can submit. The buttons say what they do ("It leaves everyone's pending list and cannot be brought back. Signatures already given stay valid…") instead of implying a cancellation the protocol does not have, and before the finaliser signs the envelope the page asks the relay once more whether the proposal was withdrawn or declined. If Hyperliquid nevertheless accepted a withdrawn proposal, the accepted receipt wins: the record follows what happened. (The finaliser's decline was retired on 2026-10-12; see "A signer's no is an objection, never a veto".)

**A result on the relay is what the finaliser's browser reported.** Only the finaliser may record a receipt, the relay derives "accepted" from the stored answer with the same rule the page uses, and other signers see it with the line "As reported by the finaliser's browser. The ledger is the proof." and a link to the ledger. An action submitted outside the tool was never discovered in Phase 3; since Phase 4 a signer's page notices it and the relay checks it for itself (see "A proposal carried out some other way" below).

**"Needs you" counts against the relay's copy; the proposal page judges against the chain.** The inbox and the rail's counts cover every treasury at once, so they use the stored signer list and threshold (each signature still recovered in the browser first). The proposal page, where something is about to be signed, reads the signer set from Hyperliquid and re-reads it before the envelope is signed. A signature from a wallet that has since left the signer set is shown as present but not counted.

**A treasury somebody else added is marked, explained and hideable.** Because every listed signer sees a treasury automatically, anyone can create a multi-sig that lists your address and add it. Nothing of yours is at risk (a signature on it acts on that account only), but it would be confusing unannounced: the rail marks it "new" until opened, the page says who added it, and "Hide from my list" removes it in this browser.

**History records changes only.** The Signing log lists what happened (proposed, signed, taken back, withdrawn, declined, accepted or rejected, carried out elsewhere, signers changed), not the ten to twenty-five look-ups a day that found nothing new; the Overview says when the signer list was last read instead. (In Phase 3 names were this browser's own; shared nicknames came with Phase 4, below.)

**The copy never promises secrecy, a price or the absence of a server.** The operator of a relay can read what is shared through it. That is stated in the Privacy Policy (`/privacy`, linked in small print at sign-in and in the footer), not as a banner on every screen, and nothing on a relay-era screen says "private", "encrypted", "only you", "free" or "no server". Every such sentence lives in `model/relay/copy.ts` and a test rejects the forbidden words; "stored in this browser only" joined the list when the history panel turned out to say it with the relay in use.

**Migrations are written by hand, and rows are parsed, not typed.** Supabase's declarative schemas do not carry policies, grants or cron rows, which are the security-relevant part of this database, so `supabase/migrations/` is hand-written SQL created with `supabase migration new`. Until the first hosted deployment the files are edited in place and replayed with `supabase db reset`. On the client there are no generated database types: a row from the relay is untrusted input, so `model/relay/rows.ts` parses each one at run time and drops what does not fit, which generated types would have waved through.

**Hyperliquid's record and the Signing log are two tabs.** A treasury page has Overview, Pending, Signing log and "On Hyperliquid". The last one is the account's own record (transfers, trades, orders, funding) in sortable tables, each with a "View more" link to Hyperliquid's page for that account; the Signing log is what happened in the tool. They are kept apart because they answer different questions and only one of them is proof. There is no "control changes" list: its only source would be the account's last hundred or so transactions, which a trading bot fills in minutes, so the list would lose entries without saying so. Signer changes are in the Signing log, an API wallet row names the proposal that approved it when there is one, and changes made elsewhere reach a signer through the notice.

**A transfer is tied to its proposal through its transaction, and "none on record" is never a guess.** The ledger says what the account did, not who proposed it. What links the two is the transaction: Hyperliquid's explorer returns, for a ledger row's hash, the action exactly as it was signed, and for a multi-sig that is the proposal's own action (measured for every kind the tool proposes; Postgres `jsonb =` agrees). So the page first asks nobody: a row can only belong to a proposal whose number is at most two days older and at most one day newer than the row, and whose kind, amount and destination agree. Only for those rows is the transaction looked up (weight 40, once per hash for the session, five at once and then one every three seconds) and compared key by key. The cell says "checking…" until then and "could not check" if the explorer does not answer; "none on record" is said only after the comparison, or when no proposal could match at all. Two proposals with the same action and number (they differ only in the finaliser) cannot be told apart by the chain, and the cell says so.

**A proposal carried out some other way is closed by the relay, after the relay looked for itself.** When a signer's page sees a ledger row whose transaction is an open proposal's action, it tells the relay the hash. The relay does not believe the page: after 30 seconds (a finaliser's own slow report must not be mistaken for "outside") its worker fetches the transaction from the explorer and requires the treasury as the account, no error, and the action equal to the stored document's. Then the proposal is closed as "Carried out outside this tool" for everyone, with the transaction linked. A wrong or unknown hash is rejected and changes nothing; twins are never closed automatically; a finaliser's receipt that arrives later turns it into an ordinary "accepted", said once in the log. The worker still makes one outbound call per step, and an explorer call counts double against its budget.

**A proposal whose finaliser has left the signer set "cannot be finished".** Hyperliquid accepts an envelope only from a current signer. The page compares the signer set recorded when the proposal was made with the live one and, if the finaliser was a signer then and is not now, says so, asks nobody to sign, and offers "Re-propose". A finaliser that never was a signer is left alone: a document made elsewhere may name a funded API wallet.

**USDC sends go in order, and the tool says so before anyone runs into it.** Found on testnet during Phase 4 and not documented by Hyperliquid: once an account has carried out a `usdSend`, a `usdSend` with an older `time` is refused with "Nonce already used.", whoever leads and wherever it sends; class transfers, spot sends and API wallet approvals are taken in any order, and a failed attempt does not count (twelve recorded pairs, `fixtures/multisig/send-order.json`). Two payments pending at once are normal for a treasury, so carrying out the newer one first would silently kill the older. The rule is in the core (`multisig/order.ts`, errors 1.3.0, multisig 1.1.0) and the section uses it three ways: an older pending send reads "Cannot be submitted any more" with "Re-propose" once a newer one went through (known from the proposals on record, from a recorded refusal, and on the proposal page from the ledger and the explorer, which also catches sends made with another tool); the inbox lists such proposals under "Cannot be finished" and lists what a finaliser can submit oldest first; and the finaliser is warned before submitting a send while older ones still wait.

**What the order lab added (2026-10-11).** The rule above came from one accident and twelve pairs, so it was put to the test properly: 247 questions to a plain account and to the lab multi-sig, 27 kinds of action, each as "newer first, then an older number that was never used" (`fixtures/multisig/nonce-order.json`; the core's `overtakenBy` predicts every answer). Only `usdSend` is ordered. `sendAsset`, spot sends, class transfers, approvals, staking, account settings, orders and every other L1 kind tried go through in any order, before or after a send; a send does not invalidate anything but older sends and older bridge withdrawals. A plain account behaves exactly like a multi-sig, and the mark stays with the account through a conversion in either direction. The mark is the highest date carried out, and the check comes before the balance check. Three things follow for the tool. First, a send dated ahead (the three-day signing window dates it 23 hours ahead) shuts out, once carried out, every send dated before it, including one proposed an hour later with the two-day window and any send made with another tool: so a new send or withdrawal is always numbered after every one on record (`orderFloor`, `proposalNonce`; the form says so when it happens), and the longer window carries a sentence about what it does. Second, a withdrawal (`withdraw3`) older than the latest send is refused too, so it is in the rule table (`SHUT_OUT_BY`); whether a withdrawal that goes through moves the mark is not known, because no withdrawal is made in testing, and nothing is claimed about it. Third, the number set that an envelope is checked against is its finaliser's own: one who has used a hundred newer numbers with their own key can no longer submit an older proposal ("nonce too low"), which the error text already said and the lab counted exactly. One more measurement bears on what the signer should propose: in unified account mode, which Hyperliquid recommends for most users, `usdSend`, `spotSend` and `usdClassTransfer` are all switched off, and only `sendAsset` from the spot balance moves money to another account. That measurement decided how the signer sends: see the entries that follow.

**The two guided sends build `sendAsset` (decided 2026-10-11).** "Send USDC" and "Send spot token" used to build `usdSend` and `spotSend`. Three things spoke against that, all measured on testnet (`fixtures/multisig/send-modes.json`, `activation-fee.json`, `nonce-order.json`): `usdSend` is the one action Hyperliquid takes only in order, so two payments pending at once could kill each other; a treasury in unified account mode is refused `usdSend`, `spotSend` and `usdClassTransfer` altogether; and to an address never used `usdSend` delivers 1 USDC less than the signers approved, while `sendAsset` delivers the amount and charges the sender 1 USDC on top. Three options were weighed: keep the old actions and switch to `sendAsset` only for a unified treasury (two behaviours to explain, and the ordering trap stays for most treasuries); let the proposer pick the method (a protocol question put to someone who wants to pay an invoice); or one action for both modes. The third was taken. The mode only decides which balance the money leaves. "Raw JSON" stays the expert path for `usdSend`, `spotSend` or anything else, with the ordering warnings it always had. Proposals made before the change are shown, explained and submittable as before; "Re-propose" on one opens the new form as the equivalent `sendAsset`.

**A treasury's account mode is read, never assumed.** `userAbstraction` is asked for with the signer set and the API wallets (a third `info` request a minute while a treasury page is open) and shown as a tag with a "?". `default` and `disabled` are one thing, "manual account": two balances. `unifiedAccount` is one balance, which Hyperliquid reports with the spot balances. Two modes could not be measured: `portfolioMargin` is treated like unified and `dexAbstraction` (discontinued) like manual, each labelled as not tested; a value this version has no rule for offers what a manual account can do and says it may be refused. A mode that could not be read is not guessed either: the form offers both balances and warns where the action would be refused if the treasury turned out unified. Switching a treasury's mode from the tool is left out: through the envelope it works only with an encoding Hyperliquid does not document.

**Which balance, by default.** A manual treasury sends from the balance that holds the money (perps when both do) and delivers USDC to the receiver's perps balance, which is what `usdSend` did; both can be changed in the form. A unified treasury has nothing to choose. Neither has a unified receiver: everything lands in its one balance, so the question is not asked. "Perps ↔ spot" is hidden for a unified treasury.

**The 1 USDC for a new address is said where the destination is typed, and again where it is signed.** The form looks the destination up once it is a whole address (is it new, and its mode: two `info` reads, kept for half a minute) and says, under the field, either that sending costs nothing or that the first send costs 1 USDC, who pays it and from which balance, and when the treasury cannot pay both. The same line stands under a send written as raw JSON, where an old `usdSend` takes the dollar out of the amount. The proposal's page says it again to every signer, from a fresh look-up, and keeps asking once a minute while the address is still new, because somebody else may send to it first. A look-up that fails claims nothing: "could not be checked", and creating stays possible.

**Nothing is submitted before Hyperliquid has been asked whether it would refuse.** A refused submission uses up the proposal's number for good (the order lab), so the finaliser's page reads the treasury's mode, what it can move from each balance and whether the destination is new, right before the wallet prompt, and stops with the reason if the action would be refused as things stand. There is no override: nothing was sent, so the same proposal can be submitted once the cause is gone, and the page says so. A read that fails stops nothing, because an outage must not make a treasury unable to pay. What the mode alone rules out is known earlier and is said on the proposal's page before anyone signs, with "Re-propose" next to it.

**A unified treasury shows one balance.** Its perps figures say nothing useful (zero with nothing open, the margin in use otherwise), so the Overview and the treasury strip show Balance (the USDC total), Can be moved now and In use. What can be moved is exactly the total less what open positions and waiting orders hold: one cent more was refused on testnet, and the "after maintenance" figure Hyperliquid also reports is not what can be sent. The figures are not laid out before the mode is known, so a unified treasury never flashes a perps balance.

**The sending rules are a rule set with every recorded send behind it.** `transfers` 1.0.0 (`rules/transfers.ts`, on `/changes`): the modes, which actions each allows, where a send lands, and the activation fee per method. `multisig/transfer.ts` answers four questions from it (`accountMode`, `sendRefusal`, `landsIn`, `activationCharge`), and `test/multisig/transfer.test.ts` replays all 127 recorded sends against them. The page's sentences are in `model/send.ts` and are tested against the list of forbidden claims like the rest of the section's wording.

**A store's "restored" flag answers false while React is hydrating.** Found while testing the send form: `/multisig/propose` opened directly threw a hydration mismatch now and then. A lazily loaded route can hydrate after the root layout has already restored the persisted network, and `useNetworkHydrated` started from what the store said at that moment, while the server had rendered "not yet". Both persisted stores now go through `usePersistHydrated` (`src/store/hydrated.ts`), which reads the flag with `useSyncExternalStore` and a server snapshot of false; a jsdom test hydrates a server-rendered probe against a store that is already restored.

**Captures of a unified treasury come from one made of lab keys only.** The unified test treasury used for signing has a wallet account among its signers, and those addresses stay out of the repository. A second unified 2-of-3 of lab keys was made for the committed captures.

**Nicknames belong to one treasury and are shared by its signers.** A nickname is optional, shown only inside its treasury, and always next to the address, because it is the address that gets signed. A signer's own address can be named only by that signer, anything else by any signer; no wallet signature is asked for, since a nickname authorises nothing. Within a treasury a nickname is unique, enforced by a unique index rather than a check in a trigger (which would race), so a look-alike address cannot be given the Auditor's name. A nickname may not look like an address or be one of the words the screens use themselves ("You", "Someone"). The browser applies the same rules again to every row it reads, so a row edited in the database is ignored. Before a wallet prompt the destination is shown with its full address and who gave the nickname and when. When an address becomes a signer, a nickname others had given it is dropped. The wording is "used only in this treasury", never "private": the relay's operator can read it. A name typed for a treasury in Phase 3 stays in that browser and is offered as the starting value, never uploaded by itself.

**"Seen" marks are shared; what a signer has read is their own.** An open proposal shows, for each signer who has not signed, whether they have opened it: someone waiting can tell "has not looked" from "looked and has not signed". Every signer of the treasury sees the same marks, the one about themselves included, and the panel says so. A look is recorded once, and only when someone is in fact looking: the tab in front for a second, the relay's verified copy on screen, the proposal open, and the signed-in wallet the connected one and a signer. The wording states a fact ("seen 2 hours ago, not signed") and passes no verdict. Read markers are the opposite: one append-only row per "Got it", readable only by its wallet, moving only forward, never past the newest history entry.

**"While you were away" holds finished things, and is read only when the signer says so.** Above the inbox and above a treasury's tabs: an action carried out without the reader's signature, the end of something they proposed or signed (rejected, withdrawn, declined, expired, carried out elsewhere), a change of signers or threshold, an API wallet approved or gone with no proposal on record, and money that left with no proposal on record. Not in it: a new proposal waiting (that is the inbox), a co-signer's signature (the proposal's page), money arriving and trades (the tables), and whatever the reader did themselves. One line per proposal, for how it ended; an API wallet approved through a proposal is said once. Showing the notice or following "View" marks nothing: each treasury has "Got it" and the home screen "Mark all as read". The first marker is written silently at the newest history entry, so the notice starts from now and never replays the past.

**What only Hyperliquid knows is asked for sparingly, and nothing is said before it is known.** API wallets and transfers are not in the relay, and the WebSocket is for the treasury on screen. The notice therefore makes two one-off HTTP reads per treasury (the API wallet list, the ledger since the marker): the home screen for its first ten treasuries, one at a time; a treasury's page for itself; each at most once in five minutes, and again when a tab left open is looked at. A transfer is called unexplained only after its transaction was compared with the proposals on record; one that could not be checked stays unread, because "Got it" moves the marker only up to just before it. A marker that does not know the treasury's API wallets yet is given the list the first time it is read, without showing anything.

**Attention without notifications.** The browser tab's title carries the count of what needs the signer ("(3) Multisig — hl-tools"), a pending proposal in its last day says "expires in 17 hours", and the navigation carries a dot where the notice has something. Nothing is sent anywhere: no desktop notification, no e-mail, no chat message. Those need a channel, consent and a sender, and are a later decision.

**Local time in the section, UTC on hover.** Signers think in their own day; exports, the Details panel and the developer tools stay in UTC. Date and time are formatted separately and joined by the code, because how a runtime glues the two differs between engines and a column should not.

**Help is one small component and one checked file.** `hub/Hint.tsx` is a "?" that opens on hover, keyboard focus and tap, stays open after a tap, closes on Escape or a click elsewhere and never takes the focus. Its thirty texts live in `model/help.ts`, written for someone who has never used a multi-sig, and are tested like the relay's copy: no promise of secrecy, price or serverlessness, none of the developer's words (nonce, digest, envelope…), each short enough to read in one go.

**Live money covers the main perps market and spot.** If a treasury holds something in a builder-deployed market the Overview says so and links to Hyperliquid, rather than showing a total that leaves it out.

**The person brings the account; the page never makes or holds a key.** (Phase 5.) Creating a treasury means converting an existing account with that account's own key, in the owner's wallet. A page that generated a fresh account, converted it and threw the key away would be shorter to use, but it puts a key in the page, leaves the HyperEVM side of the address unreachable for good, and makes "convert back" hand the account to nobody. It was considered and put off.

**The wizard converts the wallet that is signed in, and nothing else.** One identity for the whole flow: signed in = connected = the account being converted. The page opens with "You are converting your own account, 0x…" and a sign-out button for converting a different one. No step asks for another account in the middle (a switch mid-flow is where "which address is this now?" bugs come from), and no line reasons from a second identity. Signed out, a different wallet connected, or the relay unreachable show the section's ordinary sign-in gate. A build without a relay has no sign-in, so there the account is the connected wallet and nothing is registered.

**Three levels, and no confirmations.** In the wizard and in "Change signers" a thing is *blocked* only when Hyperliquid itself would refuse it (the button is off and the reason stands beside it), a *warning* is one amber line with no click, and everything else is *shown* as a plain fact. No pop-up, no "I understand" checkbox, no typing to confirm: the wallet prompt is the confirmation. What Hyperliquid refuses was measured first (`fixtures/multisig/plain-convert.json`): an account that never received funds, a signer that never did, a vault or a sub-account as a signer, the account in its own list, more than ten signers. An API wallet as a signer is only a warning, because `userRole` cannot tell a funded one (accepted) from an unfunded one (refused). One form rule bends this: "Nothing changes yet" turns the Change signers button off although Hyperliquid would take an unchanged set.

**Nothing is preselected for how many must sign.** A default would silently decide "2 of 2" for someone who pasted two addresses. The number is one row of buttons, none chosen; under it two lines say what the number trades ("Stolen keys: 1 is not enough to move anything. 2 are." and "Lost keys: with 1 lost it still works. With 2 lost it is locked for good."). When signers are removed until the number no longer fits, it is cleared, never adjusted.

**A new signer is looked up once, two addresses at a time.** Each costs `userRole` (weight 60) and `userToMultiSigSigners` (20) from the reader's own network address, and a pasted list can hold ten. `model/lookups.ts` asks about at most two at a time, never twice about an address that answered, and not at all about one removed before its turn; "Check again" asks about one. A look-up that fails is an amber line, not a block. Under the list: "The page can tell that an address is in use, not that anyone holds its key."

**The conversion is signed under a chain of the network it converts on.** Hyperliquid accepts a plain conversion under any EIP-712 chain id (measured for HyperEVM, Arbitrum and Ethereum), so the first version kept whatever chain the wallet was on and asked for no switch. On mainnet that put `chainId 998` (HyperEVM testnet) in the wallet prompt next to `hyperliquidChain: "Mainnet"`: harmless to Hyperliquid, and a contradiction to a careful signer on the one action that hands over an account (audit F-015). `convertChain` now keeps the wallet's chain only when it belongs to the network being converted on, and otherwise asks for that network's HyperEVM. The relay sign-in is different on purpose: its message carries the chain the wallet is on, because the session is not tied to a network and some wallets warn about a sign-in message that names a chain they are not on.

**Whoever signs is the account, so the signature is checked before it is sent; and "no answer" is never "nothing was sent".** Hyperliquid has no "from" field: a conversion signed by another key converts that key's account. `signUserAction` recovers the signer and refuses to hand out a signature that is not the account's ("Nothing was sent: the wallet signed with 0x…"). After posting, the signer list is read back before the page says it is done. When the request gets no answer the page reads the list to find out which way it went, and says "converted", "not converted, you can try again", or that it does not know.

**The new treasury registers itself.** The account that was converted is not one of its own signers, so the relay's rule "only a signer may add a treasury" would have left a new treasury invisible until a signer added it by hand. One relay rule was added: an account may ask for itself to be added, and the worker stores it once Hyperliquid confirms it is a multi-sig (the worker still does its own look-up; the account then read nothing of the treasury, only its own request; since 2026-10-19 it reads what its signers read, see "The treasury account itself reads its treasury"). The wizard asks right after the read-back, again twice when the relay looked a moment too early, and otherwise says that any signer can add it under "Add an existing one", which also lets the account register itself later. The history says "registered by the account itself when it was converted".

**A wallet that is itself a treasury is told so quietly.** Someone who comes back with the treasury account's own wallet gets a small "treasury account · 2 of 3" tag under the wallet (one `userToMultiSigSigners` read per wallet and network, kept five minutes) and, only on that treasury's own pages, one sentence: "You are connected as the treasury itself. Switch to one of its signers: …". Nothing is blocked. The wording never says the wallet can do nothing: an account that is a multi-sig can still be a signer elsewhere, and signs and leads there with its own key (measured).

**One form changes signers, and its only value is the action's own.** Hyperliquid has one action for the signer set, the complete new set, so "Change signers" is one form that starts from the current list and number and builds one `convertToMultiSigUser`; a replacement never passes through "2 of 4" or "2 of 2". The form's field is the action's `signers` string itself ("" while untouched, the set as JSON, `"null"` for the conversion back), so a re-proposed change opens exactly as it was. Raw JSON still refuses a signer change and points to the form.

**A signer change says what it does to the proposals still waiting.** The people who approve a change usually have other proposals open. The form and the proposal's page list each waiting proposal the change touches: a signature that stops counting ("0 of 2 left"), a proposal whose submitter is removed ("can no longer be submitted"), one that falls short, one that becomes ready. It is counted from the documents the page already holds, with the same signature count used everywhere else; no request is made. "No waiting proposal is affected" is said only when every proposal on record was read. The comparison is always with the signers Hyperliquid reports now, never with the document's unsigned note of who they were when it was made.

**A carried-out signer change reads "In effect".** Once the signers Hyperliquid reports are the ones a proposal asks for (or, for the conversion back, none), that proposal is done, whoever recorded its submission. Without this stage a co-signer who opened it from a link saw its signatures judged against the signers it had installed, and read "cannot be finished".

**Converting back is a guided choice with nothing to fill in.** It lives inside Change signers (a link under the form and on the Signers card) and is built as `"signers":"null"`, the only form Hyperliquid takes (an empty list is refused). The form says what it means: whoever holds the account's own key controls everything afterwards, alone. It warns that the account is locked for good if nobody holds that key (the page cannot know), that API wallets keep working, and that the waiting proposals can no longer be submitted. Nothing is blocked.

**"Last signed" says when, never that someone cannot.** Next to each signer: "last signed 2 days ago" or "no signature here yet", from the `signature_added` entries the relay already keeps (the newest 500 in one read; a signer that read did not reach is asked about by itself, so an old signature never reads as none). It only knows signatures that passed through the relay, and the wording stays inside that.

**What an API wallet can do is said as measured, not as assumed.** "It can trade but not withdraw" was incomplete. Hyperliquid's line is whether the money can end up with someone else: an API wallet of a multi-sig can trade with everything the treasury holds, move it between the treasury's own balances and put it into a vault, all without the signers; it cannot send to another account or withdraw (`fixtures/multisig/agent-reach.json`, rule set `multisig` 1.3.0). Every sentence about API wallets now says so, and a source scan (`src/lib/wording.test.ts`) fails on the old phrases. *An API wallet approved without a name is listed too.* Hyperliquid's `extraAgents` holds only the named ones; the one approved without a name is reported in `webData3` (`userState.agentAddress`, `agentValidUntil`). Every screen read `extraAgents` alone, so a treasury whose only API wallet had no name read "None approved. Every action needs the signers.", which is a wrong statement about who can move its money. `InfoClient.apiWallets` asks both and fails rather than show a short list (`fixtures/multisig/agent-unnamed.json`).

**A send from the treasury to itself is stopped where Hyperliquid refuses it.** `usdSend` and `spotSend` to oneself are refused ("Cannot self-transfer."), `sendAsset` into the same balance too ("Invalid send"); from one balance into the other it is taken (`fixtures/multisig/self-send.json`). The form, the check before submitting and the proposal's page follow that. A withdrawal to the treasury's own address is allowed and says what it means: on Arbitrum that address belongs to the account's own key.

**A page that signs names its network in its link.** (This entry and the ones after it, down to the local stack, come from the hardening pass after the mainnet audit of 2026-10-12; its finding numbers are in TESTING.md.) The propose form and the wizard used to take the network from the header's switch, which is one stored value for the whole site: a reload, or a second tab on the other network, could put a form for a mainnet treasury on testnet and back (F-C2). They now carry `?network=` like the treasury page does. `pageNetworkStep` is the whole rule: the link wins when the page opens, the header wins when the reader moves it, a link without a network gets the header's written into it, and the form is rebuilt (keyed by network, treasury, kind and the proposal it re-proposes) whenever any of them changes, so no field survives a change of network. On a treasury page the header's switch leaves for the inbox of the other network instead of doing nothing.

**A proposal is never carried from one network to the other.** "Re-propose" on a testnet proposal, with the header on mainnet, opened a mainnet form filled with the testnet proposal's destination and amount (F-C1). The link now names the proposal's own network, and `reproposeSource` refuses a source of another network or another treasury with a sentence ("Nothing was copied from it") instead of copying.

**The bridge's withdrawal fee is a rule, not a footnote.** Measured on both networks: the bridge keeps 1 USDC out of the amount (2 requested, 1 arrives), and a withdrawal of 1 USDC or less is refused with "Withdrawal is smaller than fee.", which uses up the proposal's number (F-011). `rules/transfers` 1.2.0 carries the fee, the form refuses such an amount where it is typed, the preview says what arrives, the check before submitting catches a raw one, and the error catalogue knows the answer (`errors` 1.7.0).

**A bridge withdrawal is tied to its proposal by its number.** Hyperliquid's ledger row for a withdrawal has its own hash and a later time, so the transaction look-up that ties sends to proposals found nothing (F-019). The row carries `nonce`, which is the action's `time` (in the bridge's unit, times 1000), and that is enough to match with no request at all.

**An address as it was typed is judged where a typo costs money.** The send and withdraw destinations and the API wallet's address get the notes the wizard already gave signers: capitals that do not match the checksum, and the zero address ("whatever is sent to it is lost"). They are warnings, by the three-level rule. A signer list that can never reach its number because it counts on the zero address stays a warning too (Hyperliquid takes it), but the page then says the plain truth where the number is chosen and above the button: nobody could ever sign, and nobody could undo it. A raw `userSetAbstraction` is refused with a sentence, like a raw signer change: Hyperliquid takes it from a multi-sig only in an encoding this tool does not build (F-022).

**A submission Hyperliquid answered is never called retryable.** The proposal page already said "cannot be sent again"; the Signing log and "while you were away" said "it can be retried" of the same refusal (F-013). One function (`afterRejection`) now words both from the HTTP status: an answer from Hyperliquid has used up the number, a request that did not get through has not.

**Signing in never costs another wallet its session.** The first version ended the old session before the wallet had signed, so a declined prompt left nobody signed in (F-002). `signIn` signs first, and a session the same wallet already had is ended on the relay only after the new one is in place. With a slot per wallet (next entry) another wallet's session is not touched at all.

**Several wallets stay signed in, and the one in use is always the connected one.** A signer who holds two of a treasury's keys had to sign in again on every switch of account, because the second sign-in replaced the first. Each wallet now keeps its session in its own slot in the browser (`hl-tools.relay.<address>`), and switching to a wallet that signed in before needs no signature. A session is two things, a short-lived access token (one hour here) and a renewal token; the slot holds both. What makes this safe to do:

- *One client per wallet, never one client whose session is swapped.* A client keeps its session in its wallet's slot, so a request made through it cannot leave under another wallet's name; there is no moment at which a request meant for A could pick up B's token. The check in every write and the relay's own guards stay as a second and third line.
- *A stored session is used only after the relay has confirmed it.* Before a slot is used, `whoami()` must name the wallet the slot is called after (`probeFor`). A session that speaks for another wallet (a slot tampered with, or filled from a wrong hint) is ended, not used.
- *The rule is one pure function over events* (`model/relay/identity.ts`): the state is about the connected wallet; every answer carries the count it was asked under and is dropped when the wallet or its session changed since (A, B, A in quick succession; a sign-out while a check was running; a sign-in that finishes after the wallet moved on). What the screens get names a wallet as in use only when it is the connected one, also in the one render where the wallet extension already says B and the state still says A. It is tested over 4,000 generated event orders besides the named cases.
- *Parked means silent.* For a wallet that is signed in but not connected nothing is read, sent or renewed, and its channel is left. The clients are made with renewal off, and only the provider turns it on, for the wallet in use.
- *"Sign out" empties the slot first.* The slot is removed at once and whatever the relay says; the session is then ended on the relay through a client that stores nothing, so a renewal on the way cannot write it back. (Before, a sign-out pressed while the relay was unreachable and the access token had run out left the session in the browser, and a reload was signed in again.) "Sign out" ends the connected wallet only; the rail lists the others, each with its own sign-out, and "Sign out all wallets".
- *The number at rest is bounded.* At most eight wallets; the least recently used is dropped and ended. The single session of before is moved into its wallet's slot once, so nobody had to sign in again for this change.

**A session that was ended stops working at once.** Testing sign-out closely turned up a gap that predates the slots: ending a session stopped its renewal token, but the access token already issued was accepted until its hour was up, because the relay asked a token only whose it is and never whether its session still exists. After "Sign out" the browser holds nothing, so this concerned a copy taken earlier (malware, an extension); such a copy could read and file rows as the wallet for up to an hour, though never sign or move funds. Two tokens exist so that the one sent with every request is short-lived and can be checked without a look-up; the relay never had the second benefit, since every request goes to the database and looks the wallet up there anyway. So the look-up Supabase recommends was added (`relay_live_sessions`): every access token names its session, Auth removes a session's row when it is signed out, and `private.current_wallet()`, which every policy, guard and trigger goes through (the channel rule included), now answers only for a session that exists, is the token's own user's, and is within its time box. In front of the API, PostgREST runs `gate.live_session()` before every request and refuses a signed-in request whose session is gone with HTTP 401 and the stable message `relay.session_ended`: without that, such a request would come back empty rather than refused, and a page could not tell "this wallet has no treasuries" from "this wallet is no longer signed in". Each wallet's client looks at every answer for that message, empties the wallet's slot and asks it to sign in again, with the reason. Two database tests hold the shape in place: no policy reads the user from the token by itself, and only the identity functions and the gate read the token. One limit remains and is stated in a test: Realtime decides who may hear a channel when it is joined and does not ask again while the socket is open, so a socket joined before the session ended goes on receiving the empty "something changed" signal until its token runs out. The signal carries nothing, nothing can be read with that session, and a new join is refused.

**A returned copy brings signatures, never a title or a note.** The title and note are signed by nobody. Merging a copy whose note had been rewritten on the way added that note to the stored proposal while the page said "Nothing new" (F-026). The stored copy's unsigned fields now stay as they are; a first copy is stored as it came.

**The section's messages carry no rule codes.** The shared issue list shows each rule's code and field path, which is right in the developer tools and noise to a signer (F-010). It has a plain mode the Multisig section uses (the code stays on hover, for a bug report), and an answer from Hyperliquid that the catalogue does not know gets one plain sentence instead of advice about the envelope's bytes.

**"Carried out, not reported here."** A proposal submitted from this page while signed out is closed by the relay once a signer's page has seen the transaction. It used to read "carried out outside this tool", which is wrong to the person who had just pressed Submit here; the sentences now say only what is known. That it closes when a signer has the treasury page open, not from the inbox, is as designed (F-004).

**A former multi-sig's waiting proposals are listed, not counted.** They can be neither signed nor submitted, so they no longer count as pending in the rail or on the tab (F-023); the page still lists them, under a line that says why, until their signing window closes.

**A signer's no is an objection, never a veto.** (Phase 6, part 1.) A signer who was against a proposal could say so only by being its proposer (withdraw) or its finaliser (decline); everybody else could only not sign, and tell the others some other way. The one hosted alternative lets any single signer cancel a proposal for everyone. That gives each signer a blocking power the treasury's own rule does not: in a 2-of-5 one person could cancel everything, and its history does not even say who did. Here a no is what its name says. Every signer can say it on any open proposal; the others see "0x… said no, 2 hours ago" on the proposal, on that signer's row, in the lists and in the Signing log; and the proposal stays open, because the number that must sign decides. Nothing about a no is on Hyperliquid: a signature already given stays valid there until the signing window closes, and the page says so where a signer who signed says no.

- *No reason is stored.* Free text shown to co-signers inside a tool they trust is where "use this address instead" would be written; a list of fixed reasons rarely fits and misleads when it almost does; and the conversation belongs in the team's own channel. A no is a row saying who, to what, and when (`public.objections` has no column that could hold more, and a database test says so).
- *One position at a time, changeable while the proposal is open.* Nothing yet, a signature, or a no. Saying no takes one's own signature back; signing takes the no back; both in the relay's triggers, in one transaction. Every change is a history entry, and the Signing log reads a change of position as one step. When a proposal closes or lapses, positions stay as they were.
- *A proposal that cannot go ahead as things stand stays open.* When the signers who have not said no are fewer than must sign ("Cannot pass as things stand"), or the finaliser said no ("Cannot be submitted as things stand": only the finaliser can submit), the page says so, says what would change it, and says when it lapses. Closing it automatically would make the last no irreversible, against the rule that a position can be changed. It is live again the moment somebody changes their mind; otherwise its proposer withdraws it or its signing window closes.
- *The finaliser's decline is retired.* It was one signer closing a proposal for everybody, for good: a veto in all but name, and a misclick cost everyone a second signature. A finaliser says no like any other signer and takes it back before submitting. Only the proposer's withdrawal still ends a proposal, and the relay refuses a decline from any client (`relay.decline_retired`). Proposals declined before stay "declined".
- *The whole rule is one pure file* (`model/relay/positions.ts`), tested as a truth table for 1 to 10 signers and sentence by sentence. Where a sentence speaks of a signer it uses the name again or "their", never "he" or "she": an address has no pronoun. A no counts only from somebody who is a signer now, like a signature.
- *When a waiting proposal lapses is said wherever it is listed*, in the reader's time and in words ("in 1 day 6 hours", minutes in the last hour), from the start: it is what decides how long a held-up proposal stays in the list. No ticking seconds: on a two-day window they add alarm, not information.
- *Limits.* It exists for signed-in teams only (links and files have no shared place for it). A wallet may say no 30 times an hour: unlike a signature it costs no wallet prompt, and each one pings the co-signers.

**Staking is three forms named by where the HYPE ends up.** (Phase 6, part 2.) Hyperliquid keeps HYPE in three places (spot, the staking balance, staked with a validator) and has three actions that each move it one place: `cDeposit`, `tokenDelegate`, `cWithdraw`. A treasury that wants "100 HYPE staked with X" would have to work out how much is already in the staking balance, propose the difference, and then propose the stake, typing amounts in the smallest unit as raw JSON. The forms ask for the end result instead ("Stake", "Return to spot", "Move to another validator"), read what is already there, and work out one proposal or two. Amounts are typed in HYPE and converted with integers (8 decimals).

- *Two proposals that are one move.* Hyperliquid's multi-sig takes one action per request, so two steps are two proposals, each signed by itself. The screens merge them: one row in every list, one page with both steps, a signer signs both in one visit, a no or a withdrawal covers both, and the finaliser clicks once (every signature first, then step 1, then step 2 only if Hyperliquid accepted step 1). What ties them is each document's unsigned `meta.steps`, the two digests in order. It is written only when set, so every other document is byte for byte what it was, and a merge never fills it in from a returned copy.
- *The relay did not change.* It keeps two ordinary proposals. Its guard reads one field of the unsigned part and passes the rest through, so the tie needed no migration. The browser files, withdraws, says no to and un-signs both rows in one statement, so both or neither; database tests pin that, and that the hourly and pending limits refuse both steps or neither. A move counts as two proposals against those limits.
- *The tie is believed only where the signed parts bear it out.* The unsigned part is signed by nobody, so a tie by itself is a claim. Two proposals are shown as one move only if both carry the same list, have the same network, treasury, finaliser and proposer, are numbered in order, and their signed actions are exactly one of three shapes: move in then stake, unstake then return, unstake from X then stake with a different Y, where the first step never moves more than the move comes to (`judgeMove` in the core). Anything else is shown as two separate proposals. A forged tie cannot dress a send up as "Staking", and a move's headline is worked out from its two actions, never from text.
- *Every validator is listed and none is recommended.* Hyperliquid reports each validator's name, state, commission, its own expected rate and total stake; the form shows all of them as reported. A validator that pays nothing as things stand (jailed, not among the ones that are paid, keeps all rewards, or an expected rate of zero) gets one amber line in the form and again for every signer, because Hyperliquid accepts such a stake all the same (measured). Which validator to trust is the signers' decision; a ranking would be this tool's opinion about other people's money.
- *Staking figures are read once a minute, and the page says how old they are.* Nothing about staking is on any of Hyperliquid's socket channels, so unlike money these figures are asked for over HTTP while the tab or the form is shown, like signers and API wallets, and again when spot HYPE changes or a step was just accepted. The validator list is not in Hyperliquid's written API documentation; when it cannot be read, the form says the address was not checked against it.
- *Blocked only where Hyperliquid refuses; a lockup holds Submit, not signing.* Hyperliquid's seven refusals for these actions were recorded, and each is predicted from what was read: the core replays the lab record, every recorded answer is predicted, and the state after each step matches. An unstake inside the lockup can be proposed and signed; Submit stays off until the lockup has ended, with the time. Two things measured on testnet shaped the wording: adding to a stake restarts the lockup of the whole stake with that validator (one amber line says so), and the end of a lockup is sharp to within two seconds (the page waits 5 seconds longer).
- *A step is never offered twice, and what is not known is not said.* A stake and an unstake leave no row in the ledger, only in Hyperliquid's staking history. "Was this step carried out?" is therefore read from that history: a row of the same kind, amount and validator, made no earlier than the proposal itself (an identical step carried out before the proposal existed is somebody else's), confirmed through the explorer when it answers. When the explorer does not answer, or Hyperliquid answered "duplicate nonce" (the number was used before, possibly by a submission that went through with its answer lost), the page says the step *may* be carried out already and never that it was not: a move then offers "the whole move again" and "only step 2" instead of one button that assumes. Sending the same proposal again cannot carry it out twice (Hyperliquid takes a number once); only proposing it again could, which is why that is where the page asks the reader to look first.
- *Proposed again, a half-done move is only what is left.* From a move's first step the form names the whole move; from its second, that step alone. For a move to another validator the whole move is always unstake then stake, so filling it in again after the unstake had landed would have unstaked twice.
- *A move is shared whole or not at all.* Every way a move leaves the page (the share with co-signers, a link, a file) carries both steps, and the relay write is one statement. Half a move in a co-signer's list is a first step its finaliser could send by itself.
- *A lockup ends by Hyperliquid's clock.* The page's "Submit opens on …" uses the device's clock with a margin, but the check before submitting asks Hyperliquid for its own time when a step is an unstake. A refused submission uses up the proposal's number and makes every signer sign again; a device a few seconds fast should not cost that.
- *Figures read as on Hyperliquid's own page.* The validator table is meant to be compared with theirs, so a total stake is cut to whole HYPE as theirs is, and the expected rate is the 7-day estimate, the one their table shows first. Where the two pages differ on purpose it is written down: a validator that keeps all rewards reads "Active" there and "keeps all rewards" here, and a return's landing time is testnet's real 5 minutes here where their page counts 7 days on both networks. A list, the log and the page name a validator the same way: the name it gave itself, always with its short address.
- *A return lands by itself.* The last leg of a return to spot is Hyperliquid's own step after its queue. The page says when it lands, and the row that then appears on "On Hyperliquid" is called Hyperliquid's own step, never "none on record".
- *The waits are a rule set with their source.* Lockup and return queue per network live in `rules/staking.ts`, each marked as measured (testnet: 2 minutes and 5 minutes) or taken from Hyperliquid's docs (mainnet: 1 day and 7 days).
- *Left out.* Fee tiers, linking a staking account and governance votes (raw JSON still reaches them), and a warning about other waiting moves that want the same HYPE.

**The explorer is asked once per account, and about a single transaction only when it has to be.** Tying a ledger row or a staking step to its proposal needs the transaction behind it: the action as it was sent, with its own number, which Hyperliquid's ledger does not carry. The explorer has two requests for that, and they are rationed differently. `txDetails` answers for one transaction. On testnet it turned out to have a daily allowance per network address ("More than 100 archived blocks queried in one day"): after about a hundred older transactions it gives that same answer to every look-up for the rest of the day, a transaction seconds old included. The page used to ask it once per row on every page load, so a few reloads of a treasury with a history used the day up. `userDetails` answers with an account's newest transactions in one go, each with its action and its transaction id. Measured on 2026-10-13: exactly 300 on mainnet and on testnet, no time range and no paging (eight spellings were tried, all ignored; Hyperliquid's own explorer page sends the same bare request and pages through those 300), and it kept answering while `txDetails` was refused. So the page reads the account's list first and takes every transaction it can from it. A transaction the list cannot have (older than the account's newest 300, which is soon for an account whose API wallet trades, since every order counts) is asked about by itself as before, and so is everything when the list cannot be read: the worst case is what the page did until now. A transaction gets one chance against a list read after it was first wanted and then the request of its own, so a transfer that lands while the page is open costs one more read of the list and nothing asks in a loop (`model/chain/accountTxs.ts`). A refusal is still an error of its own and never "unknown hash": after one, nothing is asked singly of that network's explorer for ten minutes, nothing is retried, and the rows say "could not check". What is read is kept for the session only. *Considered and not built:* keeping answers in the browser (a new device, cleared storage or a signer back after months would check everything again, and signers would see different things meanwhile), and having the relay find and store each proposal's transaction (it would also let the relay confirm "accepted" itself instead of taking the finaliser's word; left for a later brainstorm). *Limits:* `userDetails` not being stopped by the allowance was measured on one day, on testnet; whether it has an allowance of its own is unknown; mainnet's allowance is unmeasured.

**A vault action is signed as a code, under a network the wallet has to hold.** (Phase 6, part 3.) Hyperliquid has a `vaultTransfer` signed as `Agent { source, connectionId }` under the domain "Exchange" with chain id 1337. A wallet signs typed data only under a chain it is on, and no wallet knows a chain 1337: Rabby answers a switch to it with `-32603 Unrecognized chain ID "0x539"`. Once the wallet holds any network with that chain id it signs, and Hyperliquid accepts the result (measured on testnet: two code signatures and the readable envelope, accepted). Everything below follows from that.

- *The signing network.* The page offers "Add the signing network" (`wallet_addEthereumChain`), one approval in the wallet, once. The network's link comes from `VITE_CHAIN_1337_RPC_URL`; a build without it has no vault forms, and a vault proposal opened there says it can be read and checked, not signed. The name sent is "Geth Testnet", which is what Rabby's own list calls chain 1337, so its window shows no remark about the name. Nothing is ever sent on that network: the wallet only has to believe it is there while it signs. Behind the link is a stand-in (`src/lib/signingRpc.ts`, served on a developer's machine by `bun run rpc:1337`) that answers the few questions a wallet asks of any network with fixed values, refuses every transaction and keeps nothing. Its answers are one tested function, so it can be served from anywhere; where it is hosted for real is a Phase 7 question.
- *What stands in for the wallet's own check.* The wallet shows `connectionId` and `source` ("a" is mainnet, "b" testnet) and no field of the action. The page works the same code out from the action and shows it beside the action in words, on the proposal's page, a move's page and the form while "Create and sign" runs, with the sentence to compare the two. This is weaker than reading the destination in the wallet: the signer trusts that the page turned the action into the code honestly. Someone who wants a second opinion can put the document through the Inspector or another tool, which is why the document stays exportable at every stage. A hardware wallet that shows only the two EIP-712 hashes gets those under "A wallet that shows only hashes".
- *Only those who sign the vault step need the network.* The finaliser's own signature, the envelope, is a readable `SendMultiSig` under an ordinary chain. A finaliser who adds no signature to the action never leaves their network; the chain chosen in a vault form is for that signature only, and the form says so. When a click is over the wallet is put back on the chain it was on (`chainAfterSigning`), also after a refusal or a cancelled prompt.
- *wagmi is bypassed for the switch and nothing else.* Its connector refuses a chain that is not in its config before the wallet is asked. The switch and the add go to the wallet directly; signing and the error mapping stay on the path every other action uses. "Switch, else offer Add, then switch" is a pure function over a wallet-provider interface, tested against a fake wallet. "Add" is offered on any failed switch that is not the user's own refusal, because wallets do not agree on the code for "unknown chain".
- *A vault action carries no number of its own, and the page never guesses.* `vaultTransfer` is four fields (`type`, `vaultAddress`, `isDeposit`, `usd`); the proposal's number stands beside it in the request, not in it. Two identical deposits therefore cannot be told apart afterwards, and an API wallet can make the same deposit with no proposal at all. So the relay refuses a report that such a proposal was carried out (`relay.report_unnumbered`) and never closes one on a third party's word, a ledger row is tied to a vault proposal as "likely" and never as certain, and a vault step whose answer was lost reads "may be carried out already" with a pointer to "On Hyperliquid". It is closed by the finaliser's own receipt or by its proposer withdrawing it once they have looked.
- *The relay takes the code kind for exactly one shape.* Migration `relay_vault_proposals`: a document of kind "l1" is accepted only when its action is a `vaultTransfer` of exactly those four fields with no vault address and no expiry, and a `vaultTransfer` that claims to be user-signed is refused. The browser's mirror of the rule is `model/relay/push.ts`. Every other action of the family is as unshareable as before.
- *One step or two, worked out by the form.* A deposit is taken from what the perps balance can release, or from the one balance of a unified account, never from spot (measured). A manual treasury whose USDC is in spot gets two proposals, the move to perps and the deposit, shown, signed and submitted as one move. That is the fourth shape `judgeMove` accepts and the only one whose second step may be the code kind; the first step never brings more than the second uses, so the headline (the deposit) cannot understate what happens.
- *Blocked only where Hyperliquid refuses.* Seven refusals were recorded word for word (`fixtures/multisig/vaults.json`, 17 requests) and each is predicted from what was read: under 5 USDC, a closed vault, a vault that takes no deposits, an address that is no vault, more than can be moved, a withdrawal inside the lockup, more than the deposit is worth. Adding to a deposit locks all of it again (measured), which is one amber line for every signer.
- *A lockup holds Submit, unless it outlasts the proposal.* A withdrawal inside the lockup can be proposed and signed, and Submit opens when the lockup ends, as for an unstake. HLP locks four days and a proposal is open for two, three at most, so a withdrawal proposed soon after a deposit could never be submitted. The form refuses that with both lengths, and a proposal already in that state says so in amber to every reader. It is a certainty and not a guess: a lockup can be made longer by adding to the deposit, never shorter. (Found in the browser round; the first build let the proposal be made.)
- *HLP by name, any vault by address, none recommended.* The form has one button for Hyperliquid's own vault and a field for an address. A vault is shown as Hyperliquid reports it (leader and the share of profit they keep, what it holds, its past rate with "A past rate promises nothing.", its age, whether it takes deposits), and there is no list to browse. Which vault to trust with a treasury's money is the signers' decision.
- *Figures are cut, never rounded up.* A deposit's worth moves with the vault within minutes, so a balance rounded up would promise money that is not there; dust below a cent is shown to six decimals instead of "0.00". A withdrawal's ledger row can be a millionth short of what was asked (3 came back as 2.999999), and the match allows for that.
- *Vault figures are read once a minute.* Like staking, what a treasury has in vaults is on none of the channels the page listens to; it is asked for over HTTP while shown, with "Checked … ago", and a vault's own details once.
- *The lengths are a rule set with their source.* `rules/vaults.ts` holds the minimum, HLP's address per network and the lockups, each marked measured (testnet: HLP 96 hours, a user vault 20 seconds) or taken from Hyperliquid's docs (mainnet: 4 days and 1 day).
- *A history, not a notice.* The Vaults tab lists every vault deposit, withdrawal and distribution in Hyperliquid's record of the account, whoever made it, with the same last column as "On Hyperliquid": the proposal on record that agrees with the row ("likely", for the reason above), or "none on record". An API wallet can put a treasury's USDC into a vault without the signers, and such a row is then one that no proposal explains. It was considered whether "While you were away" should announce that, and decided against: that notice is about what the signers decided and about who can act for the treasury, so the approval of an API wallet is announced and what the key does afterwards is not. A treasury may come to trade through its API wallet, and a notice that listed the key's activity would bury everything else. The signers see an unexplained row when they look, and work out among themselves where it came from. The rows are the ledger's, which Hyperliquid already pushes over the socket: the tab follows that one channel more (`tabWants` in `model/tabs.ts`), asks for nothing new and looks nothing up on the explorer, because a vault row is tied to a proposal without its transaction.
- *Left out.* Sub-accounts, a vault's own leader actions and every other action of the code family.

**Removing an API wallet is the approval of nobody under its name.** Hyperliquid has no action that revokes an API wallet. An `approveAgent` naming the zero address and the wallet's name removes it (measured through a multi-sig, for a named wallet and for the one without a name). The Overview has "Remove" beside each wallet, which opens the form on that wallet (`?agent=`, the wallet's public name); the form describes it as a removal and not as an approval, without the "approves an API wallet" tag; the Approve form refuses the zero address and points to Remove; and the wallet hint says what the prompt will show, an address of all zeros and the name. Hyperliquid takes one removal at a time (`User has pending agent removal` inside about a minute) and refuses a name the account does not have (`Extra agent does not exist.`); the form says the first and the check before submitting reads the list again for the second. "While you were away" sets a removal that was carried out beside a wallet that is gone. It cannot say which wallet a removal took (its mark holds addresses, a removal names a name), so it explains a gone wallet this way only when there are at least as many removals as wallets gone.

**Both mode switches are one action, and the envelope is hashed over a one-letter code.** Switching a treasury between a manual and a unified account is `userSetAbstraction` with `unifiedAccount` or `disabled` in both directions. Through a multi-sig it works only if the finaliser's signature is made over the mode as one letter ("u", "i") while the action that is posted and the signers' own signatures keep the long word. That is not in Hyperliquid's docs; it was found by measuring (`fixtures/multisig/mode-switch.json`). The rule lives in the one place the envelope's hash is computed (`hashedEnvelopeAction` in `multisig/digest.ts`), so signing, checking and the Inspector agree; the table holds only letters that were measured (`rules/multisig.ts`, 1.4.0), the SDK oracle has an explicit case, and the Inspector says when what is hashed differs from what is sent. A switch to unified is accepted with positions and orders open; the switch back is refused while anything is open and accepted with nothing open, and the USDC then stays in spot, which the form says before anyone signs. Asking for the mode the treasury already has is accepted and changes nothing (one amber line), and one amber line names the waiting proposals that Hyperliquid would refuse in the new mode. The switch was carried out both ways with a real wallet in the browser round.

**A send from a multi-sig to HyperEVM is stopped in the form.** A token leaves HyperCore for HyperEVM by being sent to the token's system address (`0x2222…2222` for HYPE, `0x20` followed by the token's index for the others). Hyperliquid refuses that from a multi-sig ("Multi-sig user cannot transfer token to EVM", and "EVM transfer not configured" for another token's address; `fixtures/multisig/evm-transfer.json`). Both guided sends and Raw JSON say so under Destination, and the check before submitting knows the two refusals. The core's test for a system address is one function now; the cross-layer trace had its own, which recognised only token indexes below 256.

**A half-filled form is kept in this browser for a week.** The propose form and the wizard are long, and a wallet prompt, a second tab or a reload used to empty them. What was typed is now kept in localStorage (`hl-tools:multisig-drafts`, a Zustand store with `persist`, its "restored" flag through `usePersistHydrated`), one draft per network and treasury for the form and one per account for the wizard, the newest twenty, for seven days. It is written from the form's own setters a moment after typing stops, never from an effect on the form's state: the wallet and the stored values arrive late, and an effect would write the empty form over the draft. A link that asks for something else (another kind, another API wallet or vault, "propose again") shows what the link asks for and leaves the draft alone. A draft is validated field by field when it is read back, dropped when the proposal is created or the treasury is hidden, and never sent anywhere. The line above a restored form says "This browser keeps it for a week." with "Clear"; it does not say more than that about where it is.

**A receipt in a copy is its finaliser's word, or nobody's.** (Review of 2026-10-13.) A receipt says what Hyperliquid answered to a submission. It travels in the document, which anyone can edit, and nothing in the answer is signed by Hyperliquid. The page used to believe it as written: a copy saying "accepted" closed a proposal that was never sent, and a copy saying "refused" told a team to propose again while the first could still be sent. What can be checked is who reports it: a receipt carries the signature its finaliser put under the submission, over the exact request that was sent. So a copy opened from a link or a file keeps its receipt only when that signature recovers to the proposal's finaliser (`checkReceipt` in the core, called by `saveProposal`); any other receipt is left out with a sentence, and the proposal stays what it was. The request held the signatures that counted when it was sent, in the order the finaliser's copy had them, and a copy read later can hold more or hold them otherwise, so the check tries the likely selections first, then every selection in the copy's order, then every order for up to five signatures, within a budget of 2,000 tries. All 53 real receipts in the test browser passed on the first try. The check says who sent a proposal, and nothing about the answer: `response` and `httpStatus` are outside the signature, so whoever holds a true receipt can write "refused" beside the same signature (the reviewer's reply to the first fix). So a reported refusal is never the last word where Hyperliquid's own record can be asked: the proposal's page follows the account's ledger (now also for a proposal the relay does not hold, which is how such a copy arrives), and a row tied to the proposal by its number counts over the receipt ("Carried out · the refusal reported here is not Hyperliquid's record"); a row like it that could not be compared takes "propose it again" away (`ledgerEvidence` in `model/chain/match.ts`, the two branches in `model/stage.ts`). This reaches the actions that leave a row in the ledger, which are the ones that move money. An API wallet's approval, a conversion or a mode switch leaves none; a false "refused" on one of those costs a second proposal that changes nothing. The general answer is in reach and not built: since the explorer is asked for an account's newest transactions in one request, that list holds every action with its number and its error, so a proposal found in it with no error was carried out, and one found with an error was refused by Hyperliquid's own word, whatever its kind (a mode switch is listed with its one-letter code, so the comparison has to translate it; the relay's own check of a reported transaction compares the action as written and would, for the same reason, not recognise a mode switch carried out elsewhere). It belongs with the work on asking Hyperliquid's record that is left for after launch. A reported acceptance is not compared: it carries the line "As reported by the finaliser's browser. The ledger is the proof." and no more, since believing a payment that was not made costs nothing a second look does not repair, while a false refusal makes a team pay twice. Two limits are stated, not hidden. A receipt read from the relay is taken as the relay files it: the relay accepts one only from the finaliser's session, and it holds only the signatures their signers put there themselves, so a true receipt would fail the check whenever one signature travelled by link. And a finaliser can sign a submission and write down another answer than the one Hyperliquid gave. Both end the same way, with Hyperliquid's own record being asked, which is the work parked for after launch (the relay finding each proposal's transaction).

**A pasted request is judged over Hyperliquid's own writing of its inner action.** A proposal document must carry its action the way Hyperliquid hashes it (`action.not_canonical`); a request body pasted into the inspector used to be judged over its inner action exactly as pasted. Which of the two Hyperliquid does was an assumption until it was measured (review finding F-1, `fixtures/multisig/inner-form.json`): the same vault deposit, under the minimum so that nothing could move, was posted through a lab multi-sig with its fields in the usual order, in another order, and with the vault's address in capitals, and with the signers' and the leader's signatures made over one form or another. Signatures over the canonical form were accepted whatever form the body carried; signatures over any other form were refused, the leader's with "Invalid multi-sig outer signer", the signers' with "Invalid multi-sig inner signer". Hyperliquid reads the request, writes the inner action out itself, and hashes that. It is the same fact the mode switch showed from another side (its envelope is hashed over a one-letter code that is in no request) and the explorer shows a third way (it lists actions in Hyperliquid's form, not the sender's). So the inspector now brings a pasted request into the canonical form before judging it (`requestAsJudged`), says so in one amber note when the pasted form differs, and keeps the pasted action so that a signature made over it is named as that instead of as a stranger's. An action it cannot bring into that form (an unknown type) is judged as pasted, since nothing better is known. Not measured: a decimal string with trailing zeros inside a multi-sig request; for an action sent without a multi-sig that form is refused, and the canonical form drops them.

**A wallet's read markers are written one statement at a time.** The marker of "While you were away" is the newest row a signer wrote for a treasury, by id. The row trigger serialised two writes of one wallet with a lock, but a row has its id before a row trigger runs, so the lock could be taken in the other order than the ids and the marker read back was the older of the two. Ordering by anything assigned under the lock would have meant a new column and a change to every reader; taking the turn earlier needs neither. A statement trigger now takes a per-wallet lock before any row of the statement has an id (`relay_read_mark_turn`), so ids follow the order of writing. It serialises one wallet with itself only: two signers, or one signer's marks for two treasuries in one statement, never wait on each other's turn for longer than a statement.

**What somebody else wrote loses the characters that do not show.** A validator names itself on chain, a vault's leader names the vault, a proposer writes a title nobody signs. A "right-to-left override" in such a text turns around whatever is printed after it, which for a validator is its address. Nicknames were already refused with such characters; the others were shown as they came. Now the core drops them where it reads those texts (`shownLine`, `shownNote` in `multisig/shown.ts`: controls, every "format" character, line and paragraph separators), so no screen has to remember. Letters are left alone: no compatibility folding, because that would make "10²" read "102". The class is wider than the control characters: everything Unicode marks as ignorable by default (fillers that count as letters, variation selectors, the combining grapheme joiner), the braille blank, private-use characters and halves of surrogate pairs go too, and a letter keeps three combining marks (which clips some Tibetan and Thai stacks: the same price, for the same reason). Zero-width joiners go with them, which costs a label its joined emoji and some Persian and Indic spellings their exact form: for a label nobody signed that is the cheaper mistake, and it is a choice. The steps run in an order that gives the same text however often it is done (dropped first, composed after), because a title is cleaned when it is made and again when it is read. Dropping characters does not stop reordering, though: letters written right to left move the digits, brackets and dots beside them with no hidden character at all. So a name that goes into a sentence is closed off in an isolate when it holds such letters (`isolated`), and where a screen prints one inline it sits in `<bdi>`. None of it tells a letter from its look-alike in another script, and nothing could: a name is never the proof of anything, the address beside it is. For the one name that matters most, a vault calling itself "HLP", the real one is told by its address and tagged, and every other vault's name is shown as a quotation. A text that is signed, or that names something to the character, is the opposite case: an API wallet is removed by its exact name, so its name keeps every character and each hidden one is written out (`visibleText`), as is every text of an action in its description.

**A balance that is no longer live says since when.** The rule of the project is that every fetched figure shows when it was observed. Live balances were the exception: they carried a badge ("Reconnecting…", "Not updating") and no time, so an hour-old "can be moved now" looked like any other. The store now keeps the last moment Hyperliquid was heard from while the holdings were live, and the badge shows it whenever they are not ("figures as of …"). Not the time of the last balance message: an idle account gets none for hours while its figures are current, and that would call a fresh figure old.

**The notice of a signer list that differs says what the page really counts against.** A treasury page's lists are made from the relay's rows, so they count signatures against the relay's copy of the signer set; a proposal's own page judges against Hyperliquid's list. The notice used to end "Signatures are always counted against the live list", above lists that did not. Recounting every open proposal on the treasury page against the live list was the other way to make the sentence true; it was not taken, because the difference lasts seconds (the page asks the relay to look again at once) and the proposal page and `checkBeforeSubmit` already stand between a stale count and a submission. The notice now says which list is counted against until the two match, and what became of the ask: looking, refused (with the reason), or given up after six.

**A proposal page follows what this browser stores, and pushes one change at a time.** (QA of 2026-10-14, R2 and R1.) The page re-read storage only when its sync with the relay had saved something new, and skipped even that when a refetch cancelled the run. A tab that held the proposal unchanged, or whose run was cancelled, then never saw the copy another tab had saved: it stayed on "1 of 2" after the second signature, or on "Opening the proposal…" for good. Every run of the sync now puts the stored copy into the page whether or not it changed and whether or not it was cancelled (the runs are serialised by the proposal's lock, so the latest wins); only the error state waits for a run that was not cancelled. Pushes to the relay go through one queue per wallet and proposal (`model/relay/serial.ts`): a push is marked pending before its copy is saved, the catch-up does nothing while one is pending, and each push reads the relay's copy fresh, so a second push finds nothing left to send. That removed the second signature write and its 409. A write re-reads only that proposal and the open list; the server's ping refreshes the rest, and tab focus refetches nothing while the live channel is joined. A relay request that gets no answer ends after 10 seconds, and a wait that runs long says so with a way out (`shell/Slow.tsx`).

**Where a proposal reads as accepted, the browser checks Hyperliquid's record.** (R3.) A copy can be edited to say "accepted", and a finaliser can report "accepted" to the relay; neither is signed by Hyperliquid. The relay could ask Hyperliquid itself, but every signer's page would then be one server's requests against Hyperliquid's limits, and the relay is never trusted anyway. So the browser asks, with the request "On Hyperliquid" already makes: the treasury's newest 300 transactions on the explorer, matched by the proposal's number (`model/chain/record.ts`). Found: "On Hyperliquid's record" with a link. A matching entry with an error: refused, in red. Nothing found and the list reaches back past the send: amber and never folded, "Hyperliquid's record has no transaction for this proposal, so we can't confirm it went through." Older than the list: "too old to check". Sent in the last five minutes: nothing yet (the explorer lags), read again at most every 30 seconds while shown. A vault action carries no number and is never more than "likely"; a mode switch is compared through its one-letter code. The check runs on the proposal page, on the Signing log and in "While you were away"; the merge and the relay stay as they were.

**The screens use the section's own words, and a test keeps them.** "Send to Hyperliquid" (with "Once Hyperliquid accepts it, it cannot be undone."), never "submit"; "Cancel for everyone", with the line that signatures already given stay valid until the window closes; "sharing service", never "relay"; "Hyperliquid's record", never "the ledger" or "the chain"; "proposal number" and "what everyone signs" on the main path, with nonce, digest, envelope and EIP-712 under "For experts". `jargon.test.ts` parses every file of the section with the TypeScript compiler and fails on those words in any string or JSX text that reads as a sentence; a line that must use one (an expert panel, the glossary) says why in a `jargon:` comment. The glossary (`/multisig/glossary`) and the first-run card live in `model/guide.ts`, under the same forbidden claims as the relay's copy.

**What must not be missed is never folded; the rest is.** A proposal page could stack nine callouts above Sign. `model/notices.ts` sorts them into stop notices (Hyperliquid's record has no transaction or shows a refusal, Hyperliquid would refuse it now, the treasury cannot cover it, an older send it would shut out, a refused attempt, the signers changed, not saved) shown in full and first, and notes folded into "N notes". On a phone a bar at the bottom names the reader's next step and brings "Your part" into view; it never signs by itself, because what is signed is read there. The treasury tabs follow the WAI-ARIA tabs pattern (`src/lib/tabs.ts`), with the hint of the network switch as a description and not part of the radio's name.

**A newcomer gets a way in that needs no wallet.** The start page always offers "Create a treasury" (which says which wallet to connect) and "Look at a treasury" (the read-only inspector), and, until hidden, a numbered "How this works" card on the page itself, never a pop-up. A wallet that can sign a proposal sees one line about checking the destination and the amount, until the card is hidden. "Convert back" is its own choice in the propose form, the same action as the link under Change signers. There is no "who runs this" section: the GitHub link in the header is enough for now.

**Exports to a spreadsheet are CSV in UTC.** The Signing log and each "On Hyperliquid" table have "Download CSV" (`toCsv` in `src/lib/download.ts`): RFC 4180, every figure to its last decimal, addresses whole, a byte-order mark so spreadsheets read UTF-8, and a cell that a spreadsheet would run as a formula (one starting with =, +, -, @ that is not a plain number) opened with an apostrophe. Times are UTC like every export; the screens stay local. A transfer tied to a vault proposal says "likely", never more. A bridge withdrawal's row carries what was asked for (what arrives plus the fee, measured on mainnet), so it reads "−1 USDC, arrives · 2 requested, fee 1" beside the proposal that asked for 2.

**The Multisig section has room, keeps its look, and puts what is signed where it is read.** (2026-10-18.) At 1,200 px with a 252 px rail the section's pages were squeezed into narrow columns. Four visual directions were built side by side and judged by a panel of six seats (exchange design, treasury operations, signing safety, design system, accessibility, a first-time signer); the owner chose A+, today's look with more room plus what the panel asked for (TESTING.md §22). The section runs up to 1,440 px, and the site header and footer use the same container on every page so the logo does not move between Tools and Multisig; the tools' own content keeps its width. Rules that came out of the panel and now hold: a column that stays in view clears the sticky site header and sticks only while it fits the window, so nothing in it is ever out of reach; the preview of what every signer will sign is never in a box with its own scrollbar and never covered by a pinned button (the raw action folded for experts may scroll inside its code block); the propose form keeps Preview directly above Create; a proposal page opens with its status, then the action with the amount as the largest figure and every address whole; the warnings that stop a proposal are repeated above the buttons that act on it; a blocked button looks blocked; flair is one teal mark, never colours that compete with amber and red.

**The site launches on one domain, the Multisig at `hltools.tech/multisig`.** (2026-10-19, with everything below in this group.) The faucet miner keeps the keys of the wallets it generates in `localStorage` on the same origin as the Multisig's sign-in tokens, and those wallets hold small mainnet amounts while it mines. Either could be read only by script running on the site: React writes text as text and the only raw HTML is our two fixed init scripts, while a compromised package or a hijacked host would serve the same build on any domain. A second origin would therefore help only against the least likely case, and the real harm of foreign script on a signing page, a page that misstates what is signed, is the same on one domain or two. The protection is the Content-Security-Policy below.

**A sign-in token stays in `localStorage`, with no session limit for now.** Supabase's session is a 1-hour JWT and a refresh token that works once and, by default, never expires. An HttpOnly cookie would need our server between the browser and the relay on every request (the reverse of the design) and would still let script on the page act as the signer while it is open. Time-boxed sessions and an inactivity timeout are Supabase Pro settings, and the relay starts on the Free plan, so a copied token stays usable until that wallet signs out. That is a known gap: it lets someone act as that signer on the relay (read the treasuries, say no, cancel the signer's own proposals, set nicknames, post a proposal under the signer's name) and moves no money, since Hyperliquid needs the signers' own signatures. A 30-day cap of our own in `private.current_session()` was offered and declined; Pro's setting comes with the plan. Free also means a project paused after a quiet week (the pages keep working with links and files) and no automatic backups.

**Every response carries security headers, and the policy's work is on scripts.** The request middleware (`src/start.ts`) makes a nonce per response and sets `securityHeaders` (`src/lib/securityHeaders.ts`); the router writes that nonce on every script and tag it emits (`ssr.nonce`, read back in the browser from its `csp-nonce` meta), and our two init scripts take it too. So `script-src` is the site and that nonce, nothing inline without it, no `eval`. `connect-src` stays open to any https and wss host: the RPC probe and the WebSocket workbench reach whatever endpoint they are given, and a page's policy holds for the whole visit (the router never reloads the page between sections), so a narrow list for the Multisig alone would break those tools after one click and protect little, the tokens being readable from any page of the origin anyway. Styles may be inline (React and the wallet windows set them; a style runs no code), images come from anywhere over https, fonts only from the site (which also stops the WalletConnect window's Google font), the only frames allowed are WalletConnect's site check, and no site may frame ours (`frame-ancestors 'none'`, `X-Frame-Options: DENY`). HSTS for a year with subdomains, no preload; `nosniff`; `strict-origin-when-cross-origin`; camera, microphone, location, payment and USB off; a page is `private, no-cache` because it carries its own nonce. Built assets keep their immutable cache headers from the static handler. The development server sends no policy (Vite's own inline scripts need what it forbids), so changes are checked on a production build.

**Vaults ship on day one, and the site serves the signing network itself.** The link a wallet adds for chain 1337 is `/rpc/1337` on the site (`src/routes/rpc/1337.ts` over `signingRpcResponse`, the function `bun run rpc:1337` serves as well): no second service and the headers in one place. The path never changes, because a wallet keeps the link it added. While a wallet is on that network it asks the link a few questions, its own balance among them, so the host sees the address and IP briefly; the function logs nothing, and the privacy page says what the host's access log keeps.

**The launch is tested on a Railway copy of itself.** Merging is the launch (Railway deploys `main` to the domain), so the launch PR's own Railway environment gets a generated address and the production values for the testnet check and the owner's mainnet smoke test before anything is public; the stacked PRs are then merged from the top down so `main` changes once. The copy shares the hosted relay; what differs is the address (browser storage, the 1337 link a tester's wallet keeps) and that the variables are entered twice.

**The app is AGPL-3.0, the protocol core MIT.** The repository was public with no license, so "open source" was not yet true. AGPL keeps the signer open for anyone to use, change and host, while a hosted, changed copy has to publish its changes; the core in `packages/hl-core` stays MIT, a library others build on. Every dependency is permissive (MIT, Apache-2.0, ISC; the fonts OFL).

**The live site is watched from outside, and no visitor's browser reports to anyone.** An outside uptime check calls the site, `/rpc/1337` and the relay's address (which also catches a Free-plan pause); the relay's scheduled jobs get a weekly look at their run history. There is no error tracking in the browser: it would send visitors' data to a third party, which the Multisig's pages never contact. The production build leaves out the dev-only mock service worker, and the template's unused Sentry setting is gone.

**A sign-in that did not finish is one short toast.** (2026-10-19, the owner's call after the first staging sign-in.) The refusal used to be written beside both sign-in buttons as the server's own sentence plus advice about the device's clock, which was wrong for that refusal. Now `signInNotice` makes one line: "Sign-in didn't go through. Please try again.", "Sign-in cancelled in your wallet." for a decline, or a wait for too many attempts; the exact reason stays under "Details" for whoever reports a problem. The toast stays until closed or replaced by the next attempt (a decline fades), so it is not missed while the wallet window is in front. Toasts also got a solid background under their tint: a see-through one let the page's text run through its own.

**A staging address needs two entries in Supabase's allowed list.** Supabase checks a sign-in message's URI as written and, separately, its domain rebuilt as `https://<domain>/`; the second check is skipped for `localhost`, so the local stack never showed it. The staging address is listed without and with the trailing slash. hltools.tech needs neither, being the site URL's own host.

**Every amount has a Max, and money is never rounded.** (2026-10-19, after the mainnet smoke test.) The first mainnet withdrawal from HLP asked for the deposit's worth as the form listed it, `userVaultEquities.equity` (10.005691), and Hyperliquid refused it: what a withdrawal can take is `maxWithdrawable` from `vaultDetails` (10.005689), the precise value cut down to 6 decimals, and that worth sat above the precise value for 22 of 25 HLP depositors read the same day. So the list now says what Hyperliquid releases, and every amount field has a Max (`model/max.ts`): the most Hyperliquid would take now from its own figures, cut down to the action's decimals, never rounded. A send to a new address keeps the 1 USDC fee back only when no other balance pays it (cross-checked against `activationCharge` over 128 balance pairs); a send waits for its destination to be checked, since the fee depends on it; a bridge withdrawal is all of the balance (the bridge's 1 USDC comes out of it); a vault deposit is what perps can release (more can be typed, and the form moves the rest from spot); a vault withdrawal is exactly `maxWithdrawable`, with no margin, since a vault's worth moves until the proposal is sent and a margin would be a guess too: the amber line says so, and the check before sending compares again. Staking: everything that can be staked; a return takes the one validator's stake whole when there is one; a move takes the stake of the validator chosen. A read-only audit of the section found nothing signed that differs from what was typed and every comparison exact; its six small findings were fixed: a JSON number is read as `String(v)` and cut (`toFixed` rounded 4.9999995 up to 5); a vault deposit's move to perps is the smallest 6-decimal amount covering the shortfall (the typed deposit untouched); trading tables cut instead of rounding half-even, and a figure the cut would zero is shown whole; an unreadable spot hold makes the balance unknown rather than its total; a pasted action's amount that is not whole millionths is described as it came instead of throwing, and isolated margin reads add or remove by the amount's sign (Hyperliquid's docs: `isBuy` has no effect). The error catalogue (1.13.0) no longer advises reading `userVaultEquities` after "Insufficient vault equity for withdrawal".

**The owner's first review of the live site was argued point by point, and three points went another way.** (2026-10-19, after launch.) Eighteen notes from using hltools.tech; each was weighed before anything was built. Showing a signer's own balance on the start page was dropped: signing costs a signer nothing, and it would have meant reading another account from Hyperliquid. "Give signers 3 days" needed no warning about waiting: Hyperliquid takes a proposal number up to a day ahead, so a proposal dated 23 hours ahead can be sent the moment enough have signed (the effect it does have, on the order of plain USDC sends, was already said). The Overview keeps the page's count pills rather than "(3)" in brackets, for one look across both rows of tabs. The rest is below.

**The treasury account itself reads its treasury; writing stays with its signers.** (2026-10-19, the owner's call.) The account that was converted could register itself but read nothing of its treasury, so signed in as itself it found nothing. Its own key still controls the address everywhere outside Hyperliquid's trading side, and whatever is carried out is on Hyperliquid's public record, so its proposals and history are no secret from it. `private.my_treasuries()` now includes the wallet's own treasury: every read policy built on it widens with it, and every write stays on `private.is_signer()`, in its policy and in its BEFORE trigger, which looks at the signer list only. Pings reach it so its pages stay live. In the app nothing asks it to sign (`inboxGroup`), it keeps no read marks and gets no "While you were away" (both are about what a signer decided), and its own page carries the line that says which signers to switch to. The privacy page names it among who can read; the site had launched the same day, so no sign-in notice was shown for the change.

**Outcome shares get their own tab, named by Hyperliquid's own lists.** An outcome share is listed among the spot balances as "+<encoding>" ("+102251": outcome 10225, side 1), so the Overview showed it as a token. It now has its own tab beside Balances, Positions and Open orders, named as Hyperliquid names it: `outcomeMeta` gives a plain name, a template's id or the protocol's own recurring kinds, and `outcomeTemplates` writes a template's name from the description's key:value pairs ("{perp} above {threshold} at {time}?"); a question's outcome is read with its question. Those two lists are read only while the treasury holds a share and kept ten minutes: they are metadata, not money, and the alternative was "Outcome 10225 · side 1". Shares are left out of the token count and of what a send offers (Hyperliquid's spot token list never contains them).

**A result is said twice: on the page and in a toast.** (2026-10-19, the owner's call, including that a failure closes by itself.) The page's own line stays (it is announced and scrolled into view, `Heard`), and a toast repeats it for the reader whose eyes are elsewhere: four seconds for a success, eight for a failure with its first reason, a warning for a result the page cannot call yet. The four sharing-service buttons answer with their own issue, so a push the page makes in the background never raises one.

**A proposal has a timeline, read from the history the page already has.** The sharing service's history of the proposal arrived with it and was used only to drop taken-back signatures; it now writes the timeline, oldest first. Entries of one wallet within ten seconds are one step (proposing and signing in one go, a no that takes the signature back) and further apart two decisions, which the first browser run showed was needed. Hyperliquid's record joins it only where the page reads it already (a sent proposal), and comes after the send it records. A copy alone gives what it can, and never names its proposer, which is not signed.

**Hiding a treasury is a menu choice with Undo.** "Hide from my list" sat under a sentence about who added the treasury, one click from a reader who only wanted that note gone. The note closes with ×; hiding moved to a "⋯" menu beside "Propose an action", its toast offers Undo for six seconds, and its half-filled forms go only once the hiding stands.

**The signing settings are folded, with the choice in the fold's title.** "Signers sign under" and the signing window keep their defaults for almost every proposal; folded under "Advanced", whose title names what is chosen ("signed for HyperEVM testnet · 2 days to sign"), nothing is hidden that the reader does not see named. ## Testing

**Browser testing uses the Chrome DevTools MCP.** Viewport emulation (`emulate`) gives exact desktop (1440×900) and mobile (375×812, DPR 2) sizes and light/dark `prefers-color-scheme`. The faucet miner is exercised with the Rabby wallet in that browser; mining itself is only run under the existing MSW mock harness so no real funds move.

**Every browser bug becomes a fixture or a regression test where the logic lives in core.** Examples: `@abc` malformed-prefix note (resolver cases), truncated exchange response (explain cases), rate-limited probe (probe test). Presentation-only bugs are logged in TESTING.md with the fix.

**Committed screenshots come from an isolated browser context at DPR 1.** No wallet is connected and storage is fresh, so no address or balance appears in the repository. DPR 1 keeps full-page mobile captures of long pages small enough to review and to commit.

**The root Vitest config runs the workspace projects** rather than inheriting `vite.config.ts`, whose TanStack Start/Nitro plugins kept the process alive after every run.

**A multi-sig proposal is identified by the digest signers sign, and the document keeps signed and unsigned parts apart.** `packages/hl-core/src/multisig` defines `{ payload, digest, signatures, meta, receipt }`: everything in `payload` (network, multi-sig user, leader, canonical action, nonce, vault address, expiry) is bound into every inner signature; title, note, policy snapshot and receipt are not. The digest is the EIP-712 digest actually signed (Agent struct for L1 actions, enriched `HyperliquidTransaction:*` struct for user-signed ones), so verification is one recovery for both schemes, and `validateProposal` recomputes it on every load. Title and note stay unsigned so the hash matches what the official SDKs produce (verified byte for byte against `@nktkas/hyperliquid` over 3000 random scenarios and against `hyperliquid-python-sdk` 0.24.0 vectors).

**The envelope is built in canonical key order with trimmed inner signatures, never derived from pasted order.** The chain re-serialises inner signatures without leading zero digits before re-hashing the envelope (testnet: an untrimmed inner `r` fails as "Invalid multi-sig outer signer"), so `buildEnvelope` trims and `parseEnvelope` reports untrimmed or reordered input as a warning and normalises it. The envelope's `signatureChainId` is a leader-time choice bound only into the outer signature (the chain accepted `0xa4b1` and `0x1` on testnet), so it lives in the receipt, not in the signed payload.

**Readiness is computed against the *current* signer set, never stored.** A proposal document carries only signatures; `classifySignatures` recovers each one, counts distinct authorized signers against the policy passed in, and a rotation that removes a signer silently un-readies the proposal. A leader outside the signer set is `needs-lookup` (warning), because an API wallet of a signer may lead once the agent address holds a deposit (testnet, 2026-10-07) and only the info API can tell.

**Lab recordings are fixtures.** `fixtures/multisig/lab-envelopes.json` holds the 124 real testnet requests of the multi-sig lab (public data only, extracted by `scripts/extract_lab_envelopes.ts` from the gitignored `labs/multisig/runs`), with the signer policy in force at each. `lab.test.ts` requires every signer to recover to a lab wallet unless the recording deliberately diverged, readiness to predict every threshold/signer rejection, every error string to map to the catalogue, and `diagnoseSignature` to name every injected divergence. The multisig module is held to 100 % line and branch coverage (`vitest.config.ts` thresholds scoped to `src/multisig`).

**The app has its own Vitest project for pure logic.** The signer's model (`src/components/multisig/model/`) and the shared helpers are tested under a second project in the root config: node environment, the `#` alias resolved by hand, `fake-indexeddb` per suite, still without `vite.config.ts` and its plugins. `roundtrip.test.ts` is the browser milestone offline: build, create, sign, save, publish as a link, decode, sign as the finaliser, classify, build and sign the envelope, submit to a fake exchange that asserts the canonical body, store the receipt. Deterministic keys live in `src/test/keys.ts`. Components are verified in the browser, not in jsdom.

**The signer milestone was run with the wallet's own accounts, never with lab keys.** Rabby in the DevTools-controlled browser holds a treasury and three signers created from its seed, funded and converted to a 2-of-3 through Hyperliquid's official testnet UI; every approval popup was driven through the extension page. No private key was read, typed or stored, which is also the product's promise. The lab treasury (keys in the gitignored lab) is used only for read-only checks and for the committed screenshots.

**The relay is tested in three layers, each where its logic lives.** Access rules, guards, the look-up state machine and the worker are pgTAP tests that run inside Postgres (`supabase/tests/`, 450 assertions): they act as real wallets with real `auth.identities` rows, against synthetic `0x7e57…` addresses, inside a transaction. The client functions run against the local stack in an opt-in Vitest project (`bun run test:relay`, 33 tests) with deterministic keys and a stub info server: real wallet sign-in, two clients signing at once, pings arriving, an outsider refused on every table. Everything that decides something without the network (assembling a proposal from rows, the inbox groups, what to push, the history sentences, the reconnect and re-check schedules, the forbidden-word check) is a pure function in `model/relay/` with unit tests. Components are verified in the browser.

**The relay's browser tests mix the wallet's accounts with lab keys.** A treasury whose three signers are all in one Rabby cannot show two people working at once. The mixed test treasury is a 2-of-3 of one Rabby account and two lab keys: the browser plays one signer through real wallet prompts while scripts in the gitignored lab play the others through the same client functions the page uses (`relay/api.ts`), so "a co-signer signs and the page updates" is measured, not simulated. The scripts can also change the signer set on chain, which is how the removed-signer, threshold and frozen cases were run for real.

**Relay screenshots are taken as a lab signer, with a stand-in wallet that cannot sign.** A relay screen has to show a signed-in wallet, and the wallet's own accounts stay out of the repository. The committed captures come from an isolated browser context with no extension, where an injected EIP-1193 object answers "which account?" with a lab address and refuses everything else, and the session was made by a lab script. What is on screen is the lab treasury and proposals seeded with lab keys on testnet.

**Phase 4 is tested where each piece of logic lives, then on testnet.** The socket hub runs against a fake socket and clock; row merging has property tests; the matcher, the notice, the stage and the copy are pure and unit-tested; every new table, guard and worker path has pgTAP cases; the app's client functions run in the integration suite with an explorer stub; and each screen was driven in the browser against the local relay and Hyperliquid testnet, with lab keys playing the co-signers. A protocol rule found in that last layer is recorded and becomes a fixture: the order of USDC sends was read from twelve request pairs that are now `fixtures/multisig/send-order.json`.

**The "On Hyperliquid" captures stop above the treasury's first funding row.** The lab treasury was first funded from an address that is not a lab key. The committed captures of that tab are of a tall viewport, not of the full page, so that row is not in them.

**Phase 5 was tested with a stand-in wallet whose keys never enter the page, and with one wallet account for the milestone.** The wizard has to be signed by the account being converted, so a stand-in wallet that cannot sign (as used for the relay screenshots) was not enough. A small local process (gitignored, under `labs/`) announces an EIP-6963 wallet for a lab account to the isolated browser context and signs `personal_sign` and `eth_signTypedData_v4` requests itself, on 127.0.0.1; the lab key stays in that process. It can also sign with the wrong key or refuse, which is how those two cases were seen in the browser. The milestone itself was run in the user's browser with Rabby: a wallet account converted itself into a 2-of-3, had a signer replaced, and was converted back, every prompt read before it was approved. The captures were taken as lab accounts after a database reset, so the only treasuries in view are lab ones.
